# Open Responses Specification — Research Report (MCP & Tool Definitions)

**Sources examined**
- Prose spec (authoritative page): https://www.openresponses.org/specification — version **2026-04-24** (default); previous version **2026-01-15**.
- Repo source: `openresponses/openresponses` @ `main`, file `src/specifications/2026-04-24.mdx` (797 lines) and `src/specifications/2026-01-15.mdx`.
- Published OpenAPI: `https://www.openresponses.org/openapi/openapi.json` (= `public/openapi/2026-04-24/openapi.json`, 138,849 bytes, 108 schemas); previous `public/openapi/2026-01-15/openapi.json` (102 schemas).
- Generative pipeline: `schema/openapi.json` + `schema/openapi_filter_manifest.yaml` + `schema/openapi_additive_patches.yaml` → `bin/inline_openapi_refs.py` (`bun run spec`).
- Also checked: `/reference`, `/compliance`, `/governance`, `/changelog`, `public/llms.txt`, `CONTRIBUTING`, `src/lib/compliance-tests.ts`.

**Headline finding:** MCP appears **exactly once** in the entire published specification — a single non-normative example sentence. There is **no first-class MCP tool type in the published Open Responses spec**. However, the *repository* vendors OpenAI's complete MCP JSON-Schema components verbatim under `schema/components/schemas/MCP*.json`; these are **filtered out** of the published OpenAPI and never reachable from the published paths. This distinction is explained in §2.5 and §3.

## 1. What Open Responses is

### 1.1 Identity, maintainers, problem

**Quote (opening of the spec):**
> "**Open Responses** is an open-source specification and ecosystem for building **multi-provider, interoperable LLM interfaces** based on the OpenAI Responses API. It defines a **shared schema**, **client library**, and **tooling layer** that enable a unified experience for calling language models, streaming results, and composing agentic workflows—independent of provider."

**Problem it solves (Motivation and Overview):**
> "Modern LLM systems have converged on similar primitives—messages, function calls, tool usage, and multimodal inputs—but each provider encodes them differently. Open Responses standardizes these concepts, enabling:
> - **One spec, many providers:** Describe inputs/outputs once; run on OpenAI, Anthropic, Gemini, or local models.
> - **Composable agentic loops:** Unified streaming, tool invocation, and message orchestration.
> - **Easier evaluation and routing:** Compare providers, route requests, and log results through a shared schema.
> - **Blueprints for provider APIs:** Labs and model providers wanting to expose their APIs in a common format can easily do so."

**Normative language:** BCP 14 / RFC 2119 / RFC 8174 keywords ("MUST", "SHOULD", "MAY"...) are normative "when, and only when, they appear in all capitals".

**Is it a fork/standardisation of OpenAI's Responses API?**
Standardisation *of* it, not a fork *from* it. Governance mission text:
> "The mission of the Project is to define, maintain, and promote an open, vendor-neutral API specification for interacting with large language models, **inspired by and interoperable with** the OpenAI `/v1/responses` API."

Critically, the spec is generated by **filtering a vendored copy of OpenAI's own OpenAPI**. `CONTRIBUTING` states:
> "The OpenAPI source files under `schema/` are copied from OpenAI's first-party API, so keep those files pristine. Put Open Responses metadata, including `x-openresponses-added-in`, in `schema/openapi_additive_patches.yaml`, then regenerate the spec."

So: OpenAI's schema is the substrate; a filter manifest (`schema/openapi_filter_manifest.yaml`) prunes it down to the agreed cross-vendor subset; additive patches add Open Responses–specific fields. Root manifest is titled `"title": "OpenAI API", "version": "2.3.0"` before filtering.

**Maintainers** (from `CONTRIBUTING`, per governance §2 "recorded in the Project's `CONTRIBUTING` file"):
- **Lead Core Maintainer:** Steve Coffey, OpenAI
- **Core Maintainers:** Ankit Mathur (Databricks), Anthony Liguori (Amazon), Ben Burtenshaw (HuggingFace), Devon Rifkin (Ollama), Ji Huang (OpenAI), Matt Apperson (OpenRouter), Shaun Smith (HuggingFace)

Governance constraints: "All governance roles are held by individuals, not organizations. No seats are reserved for specific companies. No single vendor may control a majority of Core Maintainer seats." TSC = all Core Maintainers + Lead Core Maintainer.

**Key principles named in the spec:** Agentic Loop, Items (bidirectional), Semantic events, State machines.

### 1.2 Top-level request/response shape

**Endpoints** (published paths — only two):
- `POST /v1/responses`
- `POST /v1/responses/compact`
- Plus (2026-04-24, added) a **WebSocket transport at the same `/v1/responses` resource**: "A WebSocket connection is a transport mode for the Responses API; it does not define a separate response object model." Clients open a turn with `{"type":"response.create", ...}`.

**Transport requirements (HTTP):**
- Request headers `Authorization` (required) and `Content-Type` (required); request bodies MUST be `application/json`.
- Non-streaming response body MUST be `application/json`.
- Streaming MUST use `Content-Type: text/event-stream`; the terminal event MUST be the literal string `[DONE]`. "The `event` field MUST match the `type` in the event body. Servers SHOULD NOT use `id`."

(**NOT SPECIFIED** as an enum in the published OpenAPI; the prose names `queued`, `in_progress`, `completed`, `failed`, `incomplete` across examples.)

**`truncation` prose:**
> - `"auto"`: The server MAY truncate earlier parts of the context... Providers SHOULD apply sensible heuristics (e.g., preserving system messages and recent turns)...
> - `"disabled"`: The server MUST NOT truncate any input. If the combined context exceeds the model's maximum context window, the request MUST fail with an error instead of silently dropping content.

**`service_tier` prose:**
> "The `service_tier` field is a hint to the provider about how urgently and reliably a given request should be processed... Servers MAY expose multiple tiers (for example, `standard`, `priority`, or `batch`)..."

Note the prose example tiers (`standard`/`priority`/`batch`) differ from the OpenAPI enum (`auto`/`default`/`flex`/`priority`) — an internal inconsistency in the spec.

**`previous_response_id` prose:**
> "When `previous_response_id` is provided, the server MUST load both the input and output associated with that prior response and treat them as part of the new request's context." Model is sampled over `previous_response.input` + `previous_response.output` + `input`, and the server "MUST preserve the semantic order".

### 1.3 Items

**Definition:**
> "**Items** are the fundamental unit of context in Open Responses: they represent an atomic unit of model output, tool invocation, or reasoning state. Items are bidirectional, they can be provided as inputs to the model, or as outputs from the model."

Four stated principles, each with its own subsection:

1. **Items are polymorphic** — "Items are discriminated based on the `type` field." Example given for `message` and `function_call`.
2. **Items are state machines** — three basic statuses:
   > - `in_progress` - the model is currently emitting tokens belonging to this item
   > - `incomplete` - the model has exhausted its token budget while emitting tokens belonging to this item. This is a terminal state. If an item ends in a terminal state, it MUST be the last item emitted, and the containing response also MUST be in an `incomplete` state.
   > - `completed` - the model has finished emitting tokens containing the item, and / or a tool call has completed successfully. This is a terminal status and no updates may be made to the item after the item has moved into this state.
3. **Items are streamable** — "The first event MUST always be `response.output_item.added`. The item is echoed in the payload with as much detail as is available at that time. For `messages`, this means at least the `role`, and for `function_call`, this is at least the `name`. All fields not marked nullable MUST have a value. Use zero values where applicable."
4. **Items are extensible** — provider-specific item types "MUST be prefixed with the canonical provider slug", e.g. `"type": "openai:web_search_call"`.

**Required fields on every Item** (from "Extending Items"): `id`, `type`, `status`.

**Main item types — published `ItemField` union (5 members, output side):**
`Message`, `FunctionCall`, `FunctionCallOutput`, `ReasoningBody`, `CompactionBody`.

**Published `ItemParam` union (9 members, input side):**
`ItemReferenceParam`, `ReasoningItemParam`, `CompactionSummaryItemParam`, `UserMessageItemParam`, `SystemMessageItemParam`, `DeveloperMessageItemParam`, `AssistantMessageItemParam`, `FunctionCallItemParam`, `FunctionCallOutputItemParam`.

The filter manifest removed `FileSearchCall`, `WebSearchCall`, `ImageGenCall` from `ItemField` (`deny.oneOf.Tool` / `deny.oneOf.ItemField`).

**Message item** (`Message`): required `type` (`"message"`), `id`, `status`, `role`, `content`; optional `phase` (`"commentary"` | `"final_answer"`, added 2026-04-24 via `x-openresponses-added-in`). `MessageRole` enum: `user`, `assistant`, `system`, `developer`.

**Content model:** two unions — `UserContent` and `ModelContent`, deliberately separate (prose §Content). Content parts in the published `Message.content` oneOf: `InputTextContent`, `OutputTextContent`, `TextContent`, `SummaryTextContent`, `ReasoningTextContent`, `RefusalContent`, `InputImageContent`, `InputFileContent`, `InputVideoContent`.

**Reasoning item** fields: `content` (raw trace), `encrypted_content` (opaque, provider-specific), `summary` (safe summaries) — "All three fields are optional".

## 2. Tools

### 2.1 The complete Tools section, quoted verbatim

The entire prose Tools section is 11 lines. Reproduced in full:

> ## Tools
>
> Tool-use is at the heart of modern LLM's agentic capabilities. There are generally two types of tools that can be exposed in Open Responses:
>
> ### Externally-hosted tools
>
> Externally hosted tools are ones where the implementation lives outside of the model provider's system. Functions are a great example, where the LLM is able to call the function, but the developer must run the function and return the output back to the LLM in a second request. MCP is another example, where external servers host the implementations, although control is not first yielded back to the developer.
>
> ### Internally-hosted tools
>
> Internally hosted tools are ones where the implementation lives inside the model provider's system. An example is OpenAI's file search tool, where the model is able to call file search, and the tool can execute and return results to the LLM without yielding control back to the developer.

**That is the whole section.** It contains no JSON, no field tables, and no normative MUST/SHOULD statements. All concrete tool declaration shapes live in the OpenAPI reference, not in the prose specification.

Related prose is in the later "Extending tools" section:
> "Implementers can expose their own hosted tools—distinct from standard function tools—by providing new capabilities directly within their own Open Responses implementation... When a user or model invokes a hosted tool, the implementor executes it within their own environment... and returns the result without exposing the implementation details."
>
> "**Hosted tools must have corresponding item types.** When building custom tools, the tool should have its own item type that provides developers a receipt of what occurred during tool call execution. The item at minimum should contain a representation of how the model invoked the tool, the status of the tool call, and the result from the tool."

### 2.2 Tool types defined (published spec)

**Exactly one: `function`.**

Published `ResponsesToolParam` (request-side tool union):
```json
{
  "oneOf": [{ "$ref": "#/components/schemas/FunctionToolParam" }],
  "discriminator": { "propertyName": "type" },
  "x-unionDisplay": "section",
  "x-unionTitle": "Tool Types"
}
```

Published `Tool` (response-side union) is likewise function-only. `ToolChoiceParam` and `AllowedToolChoice` are also function-only. This is a **known, open bug** in the project:

- Issue **#47** (open): "bug: ResponsesToolParam block in https://www.openresponses.org/openapi/openapi.json is broken" — "I.e., this is saying that function tools are the ONLY supported tool type. However, in .../ResponsesToolParam.json, I see a much more complete list of tool types including MCP tools, file search, web search, etc."
- PR **#49** (open, unmerged): "fix: include all documented tool types in OpenAPI spec" — "The openapi_filter_manifest.yaml was filtering ResponsesToolParam to only include FunctionToolParam, but OpenAI's Responses API supports many more tool types including file_search, web_search, code_interpreter, MCP, computer_use, and image_generation. This updates the manifest to include all officially documented tool types..."

### 2.3 Externally-hosted tools — exact JSON shape

**Spec prose: NOT SPECIFIED as a schema.** The externally-hosted category is defined only by the prose paragraph quoted above ("Functions are a great example... MCP is another example"). No `type` string, no fields, no JSON.

The only externally-hosted tool type the published OpenAPI actually defines is `function`. Exact shape, `FunctionToolParam` (request side):
```json
{
  "name": { "type": "string", "maxLength": 64, "minLength": 1, "pattern": "^[a-zA-Z0-9_-]+$" },
  "description": { "anyOf": [ { "type": "string" }, { "type": "null" } ] },
  "parameters": { "anyOf": [ { "$ref": "#/components/schemas/EmptyModelParam" }, { "type": "null" } ] },
  "strict": { "type": "boolean" },
  "type": { "type": "string", "enum": ["function"], "default": "function" }
}
```
`required: ["name", "type"]`. Note `EmptyModelParam` is `{"properties": {}, "type": "object", "required": []}` — i.e. the filter leaves `parameters` effectively unconstrained.

`FunctionTool` (the response-side echo) is:
```json
{
  "type": "function",
  "name": "string",
  "description": "string | null",
  "parameters": { "type": "object", "additionalProperties": {} } | null,
  "strict": "boolean | null"
}
```
with `strict` described as "Whether to enforce strict parameter validation. Default `true`."

Full request example from the prose spec's `allowed_tools` example:
```json
{
  "type": "function",
  "name": "get_latest_sales_report",
  "description": "Fetches the most recent sales report for the current quarter.",
  "parameters": {
    "type": "object",

```

### 2.4 Internally-hosted tools — declaration

**NOT SPECIFIED as a schema in the published spec.** Defined only by the prose paragraph ("implementation lives inside the model provider's system... OpenAI's file search tool"). OpenAI's `file_search`, `web_search`, `code_interpreter`, `computer_use`, `image_generation` schemas exist in the repo's vendored component library but are explicitly removed from the published OpenAPI by the filter manifest's `deny.oneOf.Tool: [FileSearchTool]` and `deny.oneOf.ItemField: [FileSearchCall, WebSearchCall, ImageGenCall]`.

The only declaration mechanism the spec *does* define is the **implementor-slug extension convention**:
```json
{
  "type": "implementor_slug:custom_document_search",
  "documents": [ { "type": "external_file", "url": "https://arxiv.org/example.pdf" } ]
}
```
with the expectation that hosted tools "must have corresponding item types" that carry invocation, status, and result, and are round-trippable.

### 2.5 Is there a first-class MCP tool type? — **Plainly: NO.**

In the **published Open Responses specification (2026-04-24 and 2026-01-15)**: there is **no** MCP tool type, no `{"type":"mcp"}` declaration, and no MCP item types, streaming events, or error types. `ResponsesToolParam` admits only `function`.

**Important nuance for implementers:** the repository `openresponses/openresponses` contains complete MCP schemas under `schema/components/schemas/` — `MCPTool.json`, `MCPToolParam.json`, `MCPToolCall.json`, `MCPListTools.json`, `MCPListToolsTool.json`, `MCPApprovalRequest.json`, `MCPApprovalResponse.json`, `MCPToolFilterParam.json`, `MCPRequireApprovalFilterParam.json`, `MCPRequireApprovalApiEnum/FieldEnum`, `MCPProtocolError.json`, `MCPToolExecutionError.json`, `MCPToolChoice.json`, `SpecificMCPFunctionParam.json`, `MCPToolCallStatus.json`, plus 8 `ResponseMCPCall*` / `ResponseMCPListTools*` streaming event schemas. **These are OpenAI's own schemas, vendored verbatim and kept pristine per CONTRIBUTING** (every one carries `"x-openai-class-name": "responses_common.api..."`). They are **unreachable dead weight** in the published spec:

- The filter manifest's `allow.oneOf.ResponsesToolParam` = `[FunctionToolParam]`, `allow.oneOf.Tool` = `[FunctionTool]`, `allow.oneOf.SpecificToolChoiceParam` = `[SpecificFunctionParam]`, `allow.oneOf."paths.POST /responses...event-stream.schema"` omits all `ResponseMCPCall*` events.
- Verified empirically: `public/openapi/2026-04-24/openapi.json` contains **0** schemas whose name contains `MCP`; same for the 2026-01-15 build and the root `public/openapi/openapi.json`. `https://www.openresponses.org/reference` contains **0** occurrences of "mcp".

**If the filter were relaxed (PR #49), the OpenAI-vendored MCP shape is** (exact, from `MCPToolParam.json`):
```json
{
  "type": "mcp",
  "server_label": "string",                 // required
  "server_url": "string",                   // URL of the MCP server to connect to
  "server_description": "string",           // optional human-readable description
  "headers": { "<string>": "string" },      // optional HTTP headers when connecting
  "allowed_tools": ["tool_name", ...]       // OR MCPToolFilterParam
                 | { "tool_names": ["..."], "read_only": true },
  "require_approval": "always" | "never"
                 | { "always": MCPToolFilterParam, "never": MCPToolFilterParam }
}
```
`required: ["type", "server_label"]`. Response-side `MCPTool.json` additionally requires all of `type, server_label, server_description, server_url, headers, allowed_tools, require_approval` (nullable).

`MCPToolCall` item (OpenAI-vendored): `{ type: "mcp_call", id, status, approval_request_id, server_label, name, arguments, output, error }` where `status` ∈ `{in_progress, completed, incomplete, calling, failed}` and `error` is a discriminated union of `MCPProtocolError | MCPToolExecutionError | HTTPError`.

`MCPToolChoice`: `{ "type": "mcp", "server_label": "string", "name": "string|null" }`.

**These are NOT part of Open Responses.** Treat them as OpenAI Responses API surface only.

### 2.6 `allowed_tools`

**Important:** `allowed_tools` is **not** a top-level request field in the published OpenAPI. `CreateResponseBody` has no `allowed_tools` property. It is a **variant of `tool_choice`**, expressed as `{"type": "allowed_tools", "tools": [...], "mode": ...}`. The prose places the `### allowed_tools` heading under `## tool_choice`, which is consistent with this.

**Prose, quoted:**
> "The `allowed_tools` field lets a client limit which tools the model is permitted to actually invoke, without changing the `tools` list itself. All tools are still surfaced to the model in context (preserving cacheability of the shared system prompt and tool schema), but the model MUST restrict its tool calls to the subset named in `allowed_tools`."
>
> "This is primarily a cache-preserving control surface: instead of mutating the `tools` field (which typically invalidates any prompt or schema caches), a client can use `allowed_tools` to dynamically narrow or expand the effective tool menu for a given request while reusing the same underlying tool definitions."
>
> "Servers MUST enforce `allowed_tools` as a hard constraint:
> - If `allowed_tools` is present, any tool call to a tool not listed MUST be rejected or suppressed by the server (e.g., by treating it as a model error, translating it into a direct reply, or applying provider-specific fallback behavior).
> - Providers MAY also use `allowed_tools` as a training or routing hint, but this MUST NOT weaken the enforcement guarantee."
>
> "Conceptually, `tools` defines the full tool universe visible to the model, while `allowed_tools` defines the subset that is executable for this request."

**Exact JSON shape** (`AllowedToolsParam`):
```json
{
  "type": "allowed_tools",
  "tools": [ { "type": "function", "name": "get_latest_sales_report" } ],  // minItems 1, maxItems 128
  "mode": "auto" | "none" | "required"                                      // optional; ToolChoiceValueEnum
}
```
`required: ["type", "tools"]`. `AllowedToolChoice` (in `ResponseResource`) adds a required `mode`.

Full spec example:
```json
{
  "model": "gpt-openresponses-1",
  "input": [ { "role": "user", "content": [ {"type": "input_text", "text": "Summarize the latest sales data and then draft a follow-up email."} ] } ],
  "tools": [ { "type": "function", "name": "get_latest_sales_report", "...": "..." },
             { "type": "function", "name": "send_email", "...": "..." } ],
  "tool_choice": {
    "type": "allowed_tools",
    "tools": [ { "type": "function", "name": "get_latest_sales_report" } ]
  }
}
```
> "In this request, the model is free to decide whether to call tools at all (`tool_choice: "auto"`), but if it does, it can only invoke `get_latest_sales_report`, even though `send_email` is visible in the shared `tools` list."

**Naming collision to watch:** OpenAI's `MCPToolParam` has its own nested `allowed_tools` field meaning *"a list of MCP tool names that are allowed for this server"* — a completely different mechanism from Open Responses' `tool_choice.allowed_tools`.

### 2.7 `tool_choice`

**Prose, quoted in full:**
> "The `tool_choice` field controls whether, and how, the model is allowed to invoke tools during a response. It applies to all tools exposed in the request (functions, hosted tools, etc.) and lets the client shape the model's behavior from "never call tools" to "must call this specific tool."
>
> - `"auto"` (default): The model may either call a tool or respond directly, based on its judgment of what best satisfies the request. This is the most flexible mode and is recommended for most general-purpose use cases.
> - `"required"`: The model MUST call at least one tool and should not respond directly without doing so. Use this when a tool call is the only valid way to fulfill the request (for example, "look up" or "execute" style actions that always require external data or side effects).
> - `"none"`: The model MUST NOT call any tools. It must rely solely on its internal knowledge and reasoning. This is useful for "model-only" completions, evaluations, or when tool side effects are undesirable.
>
> In addition to these simple modes, `tool_choice` also accepts a structured object to force a particular tool to be used:"
>
> ```json
> { "tool_choice": { "type": "function", "name": "fn_name" } }
> ```
>
> "In this form, the model is required to call the specified function tool `fn_name`. This is useful when the client has already decided which tool is appropriate (for example, after a UI selection or routing decision) and wants to bypass the model's tool-selection step while still letting the model construct arguments and interpret results."

**Forcing a specific tool:** the structured form is `SpecificFunctionParam` — `{ "type": "function", "name": "string" }`, both required. Since the published union is function-only, **there is no way to force an MCP tool or a hosted tool by name in the published spec.** (OpenAI's `SpecificMCPFunctionParam` — `{ "type": "mcp", "server_label": "...", "name": "..." }` — exists only in the unreachable vendored library.)

`ToolChoiceParam` published union: `SpecificToolChoiceParam` (→ `SpecificFunctionParam`) | `ToolChoiceValueEnum` (`none`/`auto`/`required`) | `AllowedToolsParam`.

### 3.2 Does the spec require anything of an MCP server?

**No. NOT SPECIFIED.**

- The spec imposes **zero requirements on an MCP server**. MCP appears solely as a named example inside a taxonomy paragraph distinguishing externally-hosted from internally-hosted tools.
- There is **no transport requirement** (no mention of JSON-RPC, stdio, Streamable HTTP, SSE), **no discovery requirement** (no `initialize`, no `tools/list`), and **no tool-result shape requirement**.
- MCP could not be a "server-side requirement" of Open Responses by construction: Open Responses is a **client↔model-provider HTTP(S) API**, not a model↔tool protocol. In the single sentence, MCP's server sits *outside* both the client and the provider ("external servers host the implementations"), and the sentence's one substantive claim is about **control flow**, not protocol: "control is not first yielded back to the developer" — i.e. MCP is *provider-mediated*, semantically closer to the internally-hosted category even though it is implementation-external.
- Notably, the spec does **not** even commit to MCP being inside the elicitation scope of an Open Responses server. The published tool schema has no MCP entry, so an Open Responses server today has no standardized way to be told "use this MCP server".

**Inference (clearly marked):** The likely intent is that an Open Responses *server/provider* would act as an MCP *client* on the developer's behalf, so MCP servers remain governed entirely by the separate MCP specification. Open Responses would then only standardize how the *developer's request* names the MCP endpoint and how the *resulting tool call/result* appears as Items. The vendored OpenAI schemas (`MCPToolParam` with `server_url`/`headers`, `MCPToolCall` item, `mcp_list_tools` item) are exactly that design — but they are **not** part of Open Responses as published.

## 4. Tool results and errors

### 4.1 Tool call item

`FunctionCall` (output side) — required: `type`, `id`, `call_id`, `name`, `arguments`, `status`.

| Field | Type | Description (spec text) |
|---|---|---|
| `type` | `"function_call"` (const) | "The type of the item. Always `function_call`." |
| `id` | string | "The unique ID of the function call item." |
| `call_id` | string | "The unique ID of the function tool call that was generated." |
| `name` | string | "The name of the function that was called." |
| `arguments` | **string** | "The arguments JSON string that was generated." |
| `status` | `FunctionCallStatus` | `in_progress` \| `completed` \| `incomplete` |

Prose example:
```json
{
  "type": "function_call",
  "id": "fc_00123xyzabc9876def0gh1ij2klmno345",
  "name": "sendEmail",
  "call_id": "call_987zyx654wvu321",
  "arguments": "{\"recipient\":\"jane.doe@example.com\",\"subject\":\"Meeting Reminder\",\"body\":\"Don't forget about our meeting tomorrow at 10am.\"}"
}
```
(`arguments` is a JSON-encoded **string**, not an object. No `status` in this prose example despite the schema requiring it.)

`FunctionCallItemParam` (input side, echoing a prior call) — required: `call_id`, `type`, `name`, `arguments`; optional `id`, `status`. `call_id` and `name` are `minLength: 1`, `maxLength: 64`; `name` pattern `^[a-zA-Z0-9_-]+$`.

### 4.2 Tool result item

`FunctionCallOutput` — required: `type`, `id`, `call_id`, `output`, `status`.

| Field | Type | Description (spec text) |
|---|---|---|
| `type` | `"function_call_output"` (const) | "The type of the function tool call output. Always `function_call_output`." |
| `id` | string | "The unique ID of the function tool call output. Populated when this item is returned via API." |
| `call_id` | string | "The unique ID of the function tool call generated by the model." |
| `output` | `string` **or** array of content parts (`InputTextContent` \| `InputImageContent` \| `InputFileContent`) | Text/image/file output of the call |
| `status` | `FunctionCallOutputStatusEnum` | `in_progress` \| `completed` \| `incomplete` |

Notable spec text on the result status:
> "Similar to `FunctionCallStatus`. All three options are allowed here for compatibility, but because in practice these items will be provided by developers, only `completed` should be used."

The request-side form `FunctionCallOutputItemParam` allows `InputVideoContent` in the array, a longer `output` string (`maxLength: 10485760`), and requires only `call_id`, `type`, `output`.

Returning a result is done by **sending a new request** (`POST /v1/responses`) containing the `function_call_output` item, optionally with `previous_response_id`. Spec example:
```json
{
  "type": "function_call_output",
  "call_id": "call_123",
  "output": "tool result"
}
```

For hosted tools the spec requires a corresponding item type carrying "how the model invoked the tool, the status of the tool call, and the result from the tool", round-trippable for "lossless rehydration".

### 4.3 Errors — Errors section quoted in full

> ## Errors
>
> Error handling in Open Responses is designed to provide clear, actionable feedback to developers and users when requests fail or encounter issues.
>
> When an error occurs, the API responds with a structured error object that includes:
>
> - **Type**: The category of the error, such as `server_error`, `model_error`, `invalid_request`, or `not_found`. These generally, but not always, map to the status code of the response.
> - **Code**: An optional error code providing additional detail about the specific problem. All common error codes are enumerated in the spec.
> - **Param**: The input parameter related to the error, if applicable.
> - **Message**: A human-readable explanation of what went wrong.
>
> Errors are also emitted as events in the streaming protocol, allowing clients to detect and respond to issues in real time while processing streamed responses. Any error incurred while streaming will be followed by a `response.failed` event.
>
> It is recommended to check for error responses and handle them gracefully in your client implementation. Display user-friendly messages or trigger appropriate fallbacks where possible.
>
> Error types can indicate whether an error is recoverable or not, allowing your application to determine if it should retry, prompt the user, or halt the operation. The error's `code` provide additional details, often including guidance or steps for recovery, which helps developers create more robust and responsive clients.
>
> ```json
> {
>   "error": {
>     "message": "The requested model 'fake-model' does not exist.",
>     "type": "invalid_request_error",
>     "param": "model",
>     "code": "model_not_found"
>   }
> }
> ```

**Error Types table, quoted exactly:**

| Error Type | Description | Status Code |
|---|---|---|
| `server_error` | The server encountered an unexpected condition and could not complete the request. This is an internal failure and is not caused by the client. Retrying later may succeed. | 500 |
| `invalid_request` | The request is malformed or semantically invalid. One or more parameters are missing, incorrectly formatted, or unsupported. This error is user-resolvable by fixing the request. | 400 |
| `not_found` | The requested resource does not exist or is not accessible at the specified path or identifier. The client should verify the endpoint or resource ID. | 404 |
| `model_error` | The model failed while processing an otherwise valid request. This indicates an internal model or execution error and is not user-resolvable. | 500 |
| `too_many_requests` | The client has exceeded the allowed request rate. Requests are being temporarily throttled. The client should slow down and retry after a delay. | 429 |

**Error codes:** the prose claims "All common error codes are enumerated in the spec", but the published OpenAPI defines **no enum of error codes** (`code` is a bare `string` in `Error`, `ErrorPayload`, and `Error`). Only three codes appear by name anywhere: `model_not_found` (example), `previous_response_not_found` (WebSocket), `websocket_connection_limit_reached` (WebSocket). **The enumerated error-code list referenced by the prose is NOT SPECIFIED / absent.**

**Error object shapes in the published OpenAPI:**
- `Error` (non-streaming): required `code` (string), `message` (string). No `type`, no `param`.
- `ErrorPayload` (streaming `error` event): required `type` (string), `code` (string\|null), `message` (string), `param` (string\|null); optional `headers` (map<string,string>).
- WebSocket error envelope: `{ "type": "error", "status": 400, "error": { "code": ..., "message": ..., "param": ... } }` — "WebSocket failures MUST be sent as a JSON `error` envelope with a `status` code and an `error.code`."

**Note the inconsistency:** the prose example uses `"type": "invalid_request_error"` while the error-types table names the type `invalid_request`.

**MCP error types:** `MCPProtocolError` (`{type:"mcp_protocol_error", code:int, message:string}`), `MCPToolExecutionError` (`{type:"mcp_tool_execution_error", content:{}}`), `HTTPError` (`{type:"http_error", code:int, message:string}`) exist **only** in the vendored OpenAI library, **not** in Open Responses.

### 4.4 Streaming event model for tool calls

Two mandated event categories:
> "**Delta Events** — A delta event represents a change to an object since its last update... Common examples: Adding a new item to a list (`response.output_item.added`)... Appending more text to an ongoing output (`response.output_text.delta` or `response.function_call_arguments.delta`)... Signaling that no further changes will occur to a content part (`response.content_part.done`)."
>
> "**State Machine events** — A state machine event represents a change in the _status_ of an object as it progresses through its lifecycle. For example, when a response changes status from `in_progress` to `completed`, a `response.completed` event is triggered."

Transport: SSE with `Content-Type: text/event-stream`, terminal `[DONE]`, `event` field MUST match `type` in the body, servers SHOULD NOT use `id`.

**Complete published streaming event set (23 events, from the `/responses` 200 event-stream oneOf):**
`response.created`, `response.queued`, `response.in_progress`, `response.completed`, `response.failed`, `response.incomplete`, `response.output_item.added`, `response.output_item.done`, `response.reasoning_summary_part.added`, `response.reasoning_summary_part.done`, `response.content_part.added`, `response.content_part.done`, `response.output_text.delta`, `response.output_text.done`, `response.refusal.delta`, `response.refusal.done`, `response.reasoning.delta`, `response.reasoning.done`, `response.reasoning_summary.delta`, `response.reasoning_summary.done`, `response.output_text.annotation.added`, `response.function_call_arguments.delta`, `response.function_call_arguments.done`, `error`.

**Function-call lifecycle, per the "Items are streamable" rules:**
1. `response.output_item.added` — MUST be first. "For `function_call`, this is at least the `name`."
2. `response.function_call_arguments.delta` (0..n) — required `type`, `sequence_number`, `item_id`, `output_index`, `delta`; optional `obfuscation`.
3. `response.function_call_arguments.done` — required `type`, `sequence_number`, `item_id`, `output_index`, `arguments`.
4. `response.output_item.done` — closes the item, carrying the full item.

Note that a `function_call` has **no content parts**; it emits argument deltas directly after `response.output_item.added` (unlike `message`, which goes `response.content_part.added` → `response.output_text.delta`* → `response.output_text.done` → `response.content_part.done`).

`response.output_item.added`/`.done` payloads carry `item` typed as `ItemField` (nullable). `response.completed` carries a full `ResponseResource`. `error` carries an `ErrorPayload` and "Any error incurred while streaming will be followed by a `response.failed` event."

`sequence_number` is "The sequence number of the event that was emitted" and is required on every event; extended events MUST include `type` and `sequence_number`.

**MCP streaming events** (`response.mcp_call.arguments.delta`, `response.mcp_call.arguments.done`, `response.mcp_call.in_progress`, `response.mcp_call.completed`, `response.mcp_call.failed`, `response.mcp_list_tools.in_progress`, `response.mcp_list_tools.completed`, `response.mcp_list_tools.failed`) are schemas present in the repo but **excluded from the published event stream** by the filter manifest.

## 5. Schema expectations (JSON Schema dialect, strictness)

**NOT SPECIFIED.** This is close to a complete negative across every axis asked about.

| Question | Answer |
|---|---|
| JSON Schema dialect used for tool `parameters`? | **NOT SPECIFIED.** No dialect named anywhere. |
| Reference to JSON Schema 2020-12? | **No.** String `"2020-12"` occurs **0** times in the published OpenAPI and **0** times in the prose spec. |
| Reference to draft-07? | **No.** `"draft-07"` / `"draft-04"` / `"json-schema.org"` each occur **0** times. |
| `$schema` keyword? | **No.** `"$schema"` occurs **0** times. |
| `additionalProperties: false` requirement? | **No.** `"additionalProperties": false` occurs **0** times; the only `additionalProperties` in the spec are open free-form objects (`"additionalProperties": {}`). |
| Union / nullable type arrays? | The spec's own schemas use `anyOf`/`oneOf` with `{"type":"null"}` for nullability (OpenAPI 3.1 style). Nothing is said about how *tool parameter* schemas should express unions/nullability. |
| `strict`? | A `strict` **boolean field exists** on `FunctionTool` / `FunctionToolParam`. That is the extent of it. |

**What the spec actually says about `parameters`:** only that it is a free-form object.
- `FunctionTool.parameters`: `"anyOf": [{ "additionalProperties": {}, "type": "object", "description": "A JSON schema object describing the parameters of the function." }, { "type": "null" }]`
- `FunctionToolParam.parameters`: `"anyOf": [{ "$ref": "#/components/schemas/EmptyModelParam" }, {"type":"null"}]`, where `EmptyModelParam` = `{"properties": {}, "type": "object", "required": []}`.

"JSON schema object" (lowercase, generic) is the only characterisation. There is no statement that it MUST be a valid JSON Schema, no dialect, no meta-schema URI, and no restriction to a supported keyword subset.

**What the spec says about `strict`:** only the field description — `FunctionTool.strict`: "Whether to enforce strict parameter validation. Default `true`." `FunctionToolParam.strict` has no description at all in the published spec. There is **no** statement that strict mode requires `additionalProperties: false`, requires all properties in `required`, or restricts the keyword subset (as OpenAI's function-calling docs do). **NOT SPECIFIED.**

**Response-format schemas** (adjacent, for completeness): `JsonSchemaResponseFormat` has `{type: "json_schema", name, description, schema, strict}`. In the published build, `schema` is degraded to `{"anyOf": [{"type": "null"}]}` — i.e. the filter has pruned the free-form schema body, another artifact of the filter pipeline.

## 6. Compatibility summary for an MCP server author

### 6.1 Is Open Responses relevant to a JSON-RPC MCP server at all?

**Effectively no.** Open Responses specifies the **client ↔ model-provider** API (`POST /v1/responses`, SSE, WebSocket). It does **not** specify the model/host ↔ tool protocol. MCP tool invocation in the Open Responses model belongs to the **provider/host**, which acts as the MCP client; an MCP server is an implementation detail behind the provider boundary.

Concretely:
- `POST /v1/responses` request bodies contain `tools` of type `function` only.
- There is no `{"type":"mcp", ...}` in the published schema, no `server_url`/`server_label` request field, and no `mcp_call` item or streaming event.
- Therefore **an Open Responses client cannot even tell a compliant Open Responses server to talk to your MCP server.** Any MCP wiring is out-of-band: provider configuration, or a non-standard provider extension.

So: **MCP is handled by the client/host (and by the MCP spec itself), not by the Open Responses server, and certainly not by the MCP server.** The single spec sentence treats MCP as an *example* of an externally-hosted tool whose control flow is provider-mediated — and then the spec never defines it.

### 6.2 Concrete, actionable requirements on an MCP server

**Required by Open Responses: NONE. There are zero.**
No transport requirement, no discovery requirement, no capability negotiation, no tool-result shape, no schema dialect, no error format, no approval/elicitation flow. The spec never addresses MCP servers.

### 6.3 What *would* matter, if you want MCP usable from an Open Responses-compatible stack

(All of the following is **inference / adjacent-spec work**, not Open Responses requirements.)

1. **Comply with the MCP specification** (JSON-RPC 2.0 over stdio or Streamable HTTP, `initialize` handshake, `tools/list`, `tools/call`). That is the only real contract; Open Responses says nothing.
2. **Expose machine-consumable JSON Schema in `tools/list`.** Open Responses' only tool-parameter affordance is a free-form "JSON schema object" fed to the model; the host will pass your MCP `inputSchema` through in some form. Nothing constrains the dialect, so **stay conservative**: draft-07/2020-12-compatible, explicit `type: "object"`, avoid exotic keywords, and consider `additionalProperties: false` since strict-mode providers commonly require it (Open Responses does not require it).
3. **Return `tools/call` results as text-plus-structured content.** Open Responses' `function_call_output.output` accepts `string` or an array of text/image/file content parts — the closest analogue. If you want your results to survive a mapping into Open Responses items, return text and/or image content rather than relying on provider-specific structured fields.
4. **Signal errors in-band via `isError`/content, not only via JSON-RPC error codes.** Open Responses' `FunctionCallOutputStatusEnum` allows only `in_progress`/`completed`/`incomplete` and notes "because in practice these items will be provided by developers, only `completed` should be used"; there is no provider-standardized tool-error item type in the published spec. MCP-side, express failures as tool results where possible.
5. **Do not rely on Open Responses features that don't exist:** `mcp` tool declarations, `server_url`/`server_label`/`headers`, `require_approval`, `mcp_approval_request`/`mcp_approval_response`, `mcp_list_tools`, `mcp_call` items and their streaming events. These are **OpenAI Responses API** surface, vendored in the Open Responses repo but filtered out of the published spec. If you target OpenAI's Responses API specifically, they apply; they are not portable Open Responses.
6. **If you control the host:** you may pass your MCP tools through as ordinary Open Responses `function` tools (`{"type":"function","name","description","parameters"}`) and route `function_call` → `tools/call` → `function_call_output` yourself. This is the only mechanism the published spec supports, and it requires **no change to the MCP server**.

### 6.4 Watch-list

- **PR #49** ("include all documented tool types in OpenAPI spec") is **open and unmerged**; if accepted, MCP declarations (`MCPToolParam`) and `mcp_call` items would enter the published schema. Until then, function-only.
- **Issue #47** tracks the same defect.
- **Issue #5** ("`ResponsesToolParam` should allow custom internally hosted tools") and **Issue #62** ("Adding Function Call Approvals in OpenResponses") are open proposals that would affect hosted-tool and approval semantics.
- Only two spec versions exist: **2026-01-15** (launch) and **2026-04-24** (WebSocket transport, `/responses/compact`, assistant-message `phase`, optional logprobs). Neither contains MCP.
