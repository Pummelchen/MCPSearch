#### L2-1 — A half-open breaker authorises an unbounded number of requests: `authorize` discards the probe refusal

- severity: S2
- unit: WebSearchCore (Search)
- file:line: `Sources/WebSearchCore/Search/ProviderHealth.swift:143`
- category: bug
- evidence: `authorize` splits on the *snapshot* state taken one `await` earlier:

  ```swift
  if snapshot.state == .open {
      let allowed = await breaker.shouldAttempt()
      if !allowed { return ProviderFailure(..., category: .circuitOpen, ...) }
  } else {
      _ = await breaker.shouldAttempt()          // ← refusal discarded
  }
  ```

  `CircuitBreaker.shouldAttempt()` is the thing that owns the invariant — its own doc comment
  says "*A half-open probe is claimed by the first caller only, so a burst of concurrent
  searches cannot all hammer a recovering provider*" (`CircuitBreaker.swift:71-74`) — and it
  returns `false` while a claimed probe is in flight (`CircuitBreaker.swift:90-93`). In the
  `.halfOpen` branch the caller throws that answer away, so `authorize` returns `nil` (proceed)
  for every request after the first. The invariant is tested only against `CircuitBreaker`
  directly (`Tests/WebSearchCoreTests/FusionAndReliabilityTests.swift:595`,
  `testHalfOpenAllowsExactlyOneProbeAfterCooldown`), never through `ProviderHealth.authorize`,
  which is the only path `SearchOrchestrator.runSingle` uses
  (`SearchOrchestrator.swift:457`). A recovering provider therefore takes the whole
  concurrent fan-out of *every* in-flight search, which is exactly the load that re-opened its
  breaker.
- expected-correct: a half-open breaker must authorise exactly one probe. The `.halfOpen`
  branch must honour `shouldAttempt() == false` and return a `.circuitOpen` failure, the same
  as the `.open` branch does (or `snapshot.state` must be re-read after the transition so the
  existing check covers it). The existing breaker test stays as-is; add the equivalent
  assertion through `ProviderHealth.authorize`.
- reproducible-by: in `ProviderHealthTests`, register `.tavily`, trip the breaker with three
  transient failures, advance a `TestClock` past the cooldown, then call
  `await health.authorize(.tavily)` twice. Today both calls return `nil`; the second must
  return a failure with `category == .circuitOpen`.
- confidence: certain

#### L2-2 — A claimed half-open probe is never released when a request ends in a bare `CancellationError`

- severity: S3
- unit: WebSearchCore (Search)
- file:line: `Sources/WebSearchCore/Search/SearchOrchestrator.swift:501`
- category: bug
- evidence: `runSingle` records health on every failure path except cancellation:

  ```swift
  } catch is CancellationError {
      result.failures.append(ProviderFailure(provider: id, category: .cancelled, message: "Request cancelled."))
  }                                            // no health.recordFailure / breaker update
  ```

  The claim itself is taken earlier, inside `ProviderHealth.authorize` →
  `CircuitBreaker.shouldAttempt()`, which sets `probeInFlight = true`
  (`CircuitBreaker.swift:92`). `probeInFlight` is cleared only by `recordSuccess`
  (`CircuitBreaker.swift:103`) and `recordFailure` (`CircuitBreaker.swift:126`), so a cancelled
  request leaves it latched for the life of the process. A bare `CancellationError` is
  produced on real paths: `URLSessionHTTPClient.send` throws it from `try Task.checkCancellation()`
  (`HTTPClient.swift:234`) and from its retry `Task.sleep` (`HTTPClient.swift:259`), and
  `runSingle`'s own `try Task.checkCancellation()` (`SearchOrchestrator.swift:479`) fires for a
  caller that was already cancelled before the fan-out began. The flag is currently *masked*
  by L2-1 (because `authorize` ignores the refusal) — the two must be fixed together, or fixing
  L2-1 alone turns this into a permanent per-provider lockout after the first cancelled search.
- expected-correct: every terminal path must release the claim — record the cancellation as a
  health outcome (as the sibling `catch` does) or add an explicit `CircuitBreaker` release that
  `runSingle` calls from the cancellation branch — so a half-open breaker can always make a
  fresh probe once the in-flight request is gone. The existing assertions on
  `state.circuit.consecutiveFailures` are unchanged; cancellation must not count as a
  transient failure for breaker *opening*.
- reproducible-by: register `.tavily`, trip the breaker with three transient failures, advance
  the clock past the cooldown, then search with a mock provider that `throw CancellationError()`
  (`MockSearchProvider` supports exactly this). Assert `await health.authorize(.tavily)` still
  allows a probe afterwards and that the breaker can still close on a success.
- confidence: certain

#### L2-3 — Providers that already reported a failure are charged a second, synthetic deadline failure

- severity: S2
- unit: WebSearchCore (Search)
- file:line: `Sources/WebSearchCore/Search/SearchOrchestrator.swift:384`
- category: bug
- evidence: the caller computes "already reported" correctly, then passes the aggregate to a
  helper that recomputes it from responses only:

  ```swift
  // runProviders, budget-expired branch (line 361)
  let reported = Set(aggregate.responses.map(\.provider))
      .union(aggregate.failures.map(\.provider))
  aggregate.attempted += ids.filter { !reported.contains($0) }.count
  await self.recordBudgetExceeded(ids: ids, answered: aggregate, into: &aggregate)

  // recordBudgetExceeded (line 384)
  let answeredIDs = Set(answered.responses.map(\.provider))   // failures ignored
  for id in ids where !answeredIDs.contains(id) { ... append .timeout failure; recordDeadlineExceeded ... }
  ```

  A provider that failed *before* the sentinel fires is not in `answered.responses`, so it gets
  a second `ProviderFailure(category: .timeout, message: "<name> exceeded the search time
  budget.")` appended, and `health.recordDeadlineExceeded` overwrites its `lastError` /
  `lastErrorCategory`. User-visible effects: `providers_failed` carries the provider twice,
  the response warning says "N provider(s) failed" with an inflated N, and
  `web_search_status` reports a deadline the provider did not cause instead of its real error.
  The gap is untested: `testProviderThatHangsIsCutOffByTheTimeBudget`
  (`SearchOrchestratorTests.swift:518`) asserts only that *some* `.timeout` failure exists.
- expected-correct: a provider that has already answered — with a response *or* a failure —
  must not be recorded again. `recordBudgetExceeded` must exclude
  `Set(answered.responses.map(\.provider)).union(answered.failures.map(\.provider))`, matching
  the `reported` set computed three lines earlier; the deadline record then applies only to
  providers that were genuinely still in flight.
- reproducible-by: balanced mode with `balancedTimeout = .milliseconds(300)`, a mock `.brave`
  that fails instantly with `.providerUnavailable(.brave)` and a mock `.tavily` that hangs
  (`MockSearchProvider.hanging`). Assert
  `response.providersFailed.filter { $0.provider == .brave }.count == 1`, its category is still
  `.serverError`, and `(await health.state(for: .brave, ...)).lastErrorCategory != .timeout`.
- confidence: certain

#### L2-4 — The session resource timeout silently caps every per-request timeout override, including the 45 s synthesis budget

- severity: S2
- unit: WebSearchCore (Support)
- file:line: `Sources/WebSearchCore/Support/HTTPClient.swift:216`
- category: bug
- evidence: `URLSessionHTTPClient.perform` honours a per-request override —
  `urlRequest.timeoutInterval = (request.timeout ?? policy.requestTimeout).seconds`
  (`HTTPClient.swift:291`) — and `HTTPRequest.timeout` is documented as "*Overrides the shared
  request timeout for this call only*" (`HTTPClient.swift:18-24`). But the session that carries
  it sets a *resource* deadline that the override cannot raise, because it is derived from the
  configuration rather than from the request:

  ```swift
  sessionConfiguration.timeoutIntervalForResource = max(
      configuration.requestTimeout.seconds * 2, 30)
  ```

  `timeoutIntervalForRequest` is the idle timeout; `timeoutIntervalForResource` bounds the whole
  task. With the shipped default (`requestTimeout = 10 s`) every request is killed at 30 s no
  matter what it asked for. `AnswerSynthesizer` is the only caller that uses the override —
  `timeout: timeout` with `configuration.synthesisTimeout` defaulting to 45 s
  (`AnswerSynthesizer.swift:312`, `AppConfiguration.swift:97`) — so grounded synthesis is
  clipped at ~30 s, and `SEARCH_SYNTHESIS_TIMEOUT_MS` above 30 000 parses correctly but has no
  effect (`CoreUnitTests.swift:173` asserts a parsed 90 s). The failure surfaces as
  `SearchError.synthesisFailed("The synthesis request failed.")` because
  `AnswerSynthesizer.describe` has no `HTTPError` case (`AnswerSynthesizer.swift:525-541`),
  which hides the reason.
- expected-correct: the transport must not impose a deadline shorter than the one the request
  asked for: either derive the resource interval from the request (set
  `urlRequest.timeoutIntervalForResource` / raise the session value to cover the largest
  configured override, e.g. `max(2 × requestTimeout, synthesisTimeout + slack)`), or remove the
  override mechanism and make the configuration authoritative. The documented override
  contract and the documented default must agree.
- reproducible-by: build `URLSessionHTTPClient` from a configuration with
  `requestTimeout = .seconds(10)` and `synthesisTimeout = .seconds(45)`; point the synthesizer
  at a loopback server that answers after 35 s and assert the synthesis succeeds. (Slow test —
  mark it opt-in, or assert the built session's `timeoutIntervalForResource` is ≥ 45 s once the
  session is reachable for assertions.) Pre-fix the call fails at ~30 s with a timeout.
- confidence: likely

#### L2-5 — `web_open` has no total deadline: a slow-drip server holds the tool call open indefinitely

- severity: S2
- unit: WebSearchCore (Fetch)
- file:line: `Sources/WebSearchCore/Fetch/DirectHTTPFetcher.swift:37`
- category: unsafe
- evidence: the fetch path builds its own session and sets the idle timeout only:

  ```swift
  sessionConfiguration.timeoutIntervalForRequest = configuration.requestTimeout.seconds
  sessionConfiguration.httpCookieAcceptPolicy = .never
  ...
  self.session = URLSession(configuration: sessionConfiguration, delegate: delegate, delegateQueue: nil)
  ```

  No `timeoutIntervalForResource` is set, so the platform default (7 days) applies; a server
  that returns one byte just inside each idle window resets `timeoutIntervalForRequest` forever.
  Nothing above it bounds the call either: `WebFetcher.open` applies no deadline of its own, and
  `ToolHandlers.webOpen` (`ToolHandlers.swift:134-141`) simply awaits it. A hostile or broken
  page therefore pins one cooperative task and one MCP tool call per request, for as long as it
  chooses. Contrast `URLSessionHTTPClient`, which does set a resource deadline
  (`HTTPClient.swift:216`) — the two transports have drifted.
- expected-correct: the fetch path must carry a total per-request deadline (a resource interval
  derived from `configuration.requestTimeout`, or a deadline enforced by `WebFetcher.open`
  across the direct attempt plus the Jina fallback) so a fetch that cannot finish inside the
  configured budget fails with a timeout instead of hanging. The budget must be at least as
  large as the existing idle timeout so legitimate slow pages keep working.
- reproducible-by: extend `LoopbackServer` with a drip response (headers first, then one byte
  every 5 s); with `requestTimeout = 2 s`, assert `DirectHTTPFetcher.fetch` throws a timeout
  within ~10 s. Pre-fix it keeps reading until the client gives up.
- confidence: likely

#### L2-6 — Cancelling `web_open` starts a *second* outbound fetch and reports a bogus error instead of propagating cancellation

- severity: S2
- unit: WebSearchCore (Fetch)
- file:line: `Sources/WebSearchCore/Fetch/WebFetcher.swift:135`
- category: bug
- evidence: cancellation is translated into an ordinary fetch error before it reaches the
  fallback decision, and the fallback then treats it as a reason to try the reader:

  ```swift
  // DirectHTTPFetcher.perform
  case .cancelled:
      throw SearchError.fetchFailed(request.url, reason: "request was cancelled")
  ...
  } catch is CancellationError {
      throw SearchError.fetchFailed(request.url, reason: "request was cancelled")
  }

  // WebFetcher.open
  } catch let error as SearchError {
      if case .blockedURL = error { throw error }      // only policy denial is special-cased
      directResult = nil
      directError = error
  }
  ...
  do {
      let jinaResult = try await jina.fetch(request, maxCharacters: request.maxCharacters)   // ← runs after cancel
  } catch {
      log.debug("Jina Reader fallback failed", ...)
      guard let result = directResult else { throw directError ?? SearchError.extractionFailed(request.url) }
  ```

  So a cancelled `web_open` (a) issues a fresh request to the reader host and (b) surfaces as
  `SearchError.fetchFailed(url, reason: "request was cancelled")` — a tool error claiming the
  remote server cancelled — rather than `CancellationError`. `JinaReaderFetcher.fetch` also
  starts with `try? await Task.sleep(for: .seconds(1))` for the unauthenticated path
  (`JinaReaderFetcher.swift:62`), which swallows the cancellation and proceeds; only the shared
  client's `Task.checkCancellation()` stops the request at the last moment.
- expected-correct: cancellation must propagate, and must never start new work: distinguish
  cancellation from a transport failure in `DirectHTTPFetcher` (rethrow `CancellationError`, or
  a dedicated `SearchError` case that `WebFetcher` rethrows immediately), rethrow it from the
  reader-fallback `catch`, and let `Task.sleep` in the reader throw rather than being discarded.
  `ToolHandlers.webOpen` already has a `catch is CancellationError` arm to receive it.
- reproducible-by: start `WebFetcher.open` against a slow loopback page with a recording mock
  reader, cancel the task while the direct fetch is in flight, then assert the task throws
  `CancellationError` and `http.requests` (reader) is empty.
- confidence: certain

#### L2-7 — The Jina Reader target is percent-encoded into a *path*, so URLs with a query or fragment fetch the wrong resource

- severity: S2
- unit: WebSearchCore (Fetch)
- file:line: `Sources/WebSearchCore/Fetch/JinaReaderFetcher.swift:43`
- category: bug
- evidence: `let target = baseURL.appendingPathComponent(request.url.absoluteString)` — the type
  is documented as "*the target URL is appended directly*" (line 9), but `appendingPathComponent`
  percent-encodes characters that are not legal in a path. Measured on this toolchain with the
  same Foundation call:

  ```
  https://r.jina.ai/https://example.com/page?q=1&x=2
  → https://r.jina.ai/https://example.com/page%3Fq=1&x=2
  https://r.jina.ai/https://example.com/page#frag
  → https://r.jina.ai/https://example.com/page%23frag
  ```

  The `?` that separates the target's query from its path is now part of the *outer path*, and
  `&x=2` is no longer a query parameter of the target at all. Query-bearing URLs are the common
  case for search results, and this is the one path that exists for pages native extraction
  cannot read. The suite only asserts a substring of the reader URL
  (`FetchFallbackTests.swift:122`), so the mis-encoding is invisible.
- expected-correct: the reader request must carry the requested absolute URL unaltered, e.g. by
  building the URL with `URL(string: baseURL.absoluteString + request.url.absoluteString)` (or
  a `percentEncodedPath`-free concatenation plus `URLComponents` that keeps the target as the
  path *without* re-encoding `?`/`#`), and a test must assert the exact URL for a query-bearing
  target rather than a substring.
- reproducible-by: `JinaReaderFetcher.fetch` for `https://example.com/page?q=1` through
  `MockHTTPClient`; assert `http.requests[0].url.absoluteString ==
  "https://r.jina.ai/https://example.com/page?q=1"`. Pre-fix the `?` is `%3F`.
- confidence: likely

#### L2-9 — `Terminal.truncate` counts ANSI escape characters as display width, so truncating styled text can drop the SGR reset

- severity: S3
- unit: WebSearchCore (Monitor)
- file:line: `Sources/WebSearchCore/Monitor/Terminal.swift:96`
- category: bug
- evidence: `truncate` walks grapheme clusters and sums `scalarWidth`, which gives every byte of
  a CSI sequence except `ESC` a width of 1 — while its sibling `displayWidth`
  (`Terminal.swift:116-136`) skips escape sequences entirely and is documented as the width
  contract ("*Counts ANSI escape sequences as zero width, which matters because styled text is
  padded after colouring*"). The two disagree, so `Renderer` can (and at narrow widths does)
  cut a styled line inside a colour run and return it without the `\u{1B}[0m` that closes it;
  the colour then bleeds into the following columns and lines. Worked example with the exact
  algorithm: `truncate("\u{1B}[91m" + 40 × "x" + "\u{1B}[0m", to: 10)` consumes
  `ESC [ 9 1 m` (4 counted units) plus 5 `x`, then stops at the limit — the result is
  `"\u{1B}[91mxxxxx…"` with **no reset**, so everything after it is red. Cuts *inside* a
  sequence are equally reachable at other widths (stopping after `\u{1B}[9` leaves an
  unterminated CSI). No test covers styled truncation: `TerminalLayoutTests` truncates plain
  text only, and `testNoLineExceedsTerminalWidth` asserts only `displayWidth`, which passes
  with a dropped reset.
- expected-correct: `truncate` must measure with the same escape-aware width as `displayWidth`
  (skip a complete `ESC [ … final-byte` run and copy it through without consuming budget), and
  must guarantee balanced SGR in its output — e.g. re-append `\u{1B}[0m` when the input carried
  an SGR opener that is not closed. Add a styled-truncation assertion; do not weaken
  `testNoLineExceedsTerminalWidth`.
- reproducible-by: `XCTAssertEqual(Terminal.truncate("\u{1B}[91m" + String(repeating: "x", count: 40) + "\u{1B}[0m", to: 10), "\u{1B}[91mxxxxx…\u{1B}[0m")` — fails today because the trailing reset is gone.
- confidence: certain

#### L2-10 — Concurrent first use of the Parallel provider performs the MCP handshake more than once

- evidence: `ensureInitialized` guards on `sessionID != nil` and then suspends several times

  e.g. cache the in-flight handshake `Task` (awaiting it from later callers) or fail fast with a

- reproducible-by: a `MockHTTPClient` that records requests for label `parallel.mcp` and answers
  `initialize`/`tools/list`/`tools/call`; launch two `provider.search` calls concurrently
  (`async let`) and assert exactly one request body carries `"method":"initialize"`.
- confidence: certain
