package on `audit/2026-09-13`: **L0 (repository)** — build reproducibility, dependency

#### L7-1 — Nothing validates configuration at startup: a mistyped value or config path is silently discarded
- severity: S2
- unit: `WebSearchCore` — `Support/AppConfiguration.swift`, `SwiftWebSearchMCP/main.swift`
- file:line: `Sources/WebSearchCore/Support/AppConfiguration.swift:252-261`, `:283-300`, `:389-391`
- category: incomplete
- evidence: every value is parsed with a silent fallback and no diagnostic is emitted for
  a value that failed to parse, and a `SEARCH_CONFIG_FILE` that does not exist is treated
  as "no config file":
  ```swift
  let fileURL =
      configFileURL
      ?? environment[Key.configFile.rawValue].flatMap { URL(fileURLWithPath: $0) }
          .flatMap { FileManager.default.fileExists(atPath: $0.path) ? $0 : nil }
  ...
  func int(_ key: Key) -> Int? { guard let raw = string(key) else { return nil }; return Int(raw) }
  func bool(_ key: Key) -> Bool? { ... default: return nil }
  func url(_ key: Key) -> URL? { guard let raw = string(key) else { return nil }; return URL(string: raw) }
  ...
  if let raw = string(.logLevel), let level = LogLevel(rawValue: raw.lowercased()) {
      configuration.logLevel = level
  }
  ```
  `url()` performs no scheme/host check (`URL(string:)` is not a validator — it accepts a
  relative string such as `searx.example.com` and returns nil for other typos, both
  silently). `main.swift:44-61` logs only the resulting provider list, so nothing anywhere
  reports that a setting was ignored, that an unparseable integer fell back to the default,
  or that the operator's `SEARCH_CONFIG_FILE` was never opened. The three failure modes are
  concrete: (a) `SEARCH_MAX_RESULTS=lots` silently becomes 8; (b) `SEARCH_LOG_LEVEL=warn`
  silently becomes `info`, because only `warning` is a case; (c) a misspelled path in
  `SEARCH_CONFIG_FILE` means no credentials are loaded at all, and the only symptom is the
  generic "No search provider is configured" warning, which does not mention the file.
- expected-correct: at boot, report (at `warning`/`error`) every configured value that
  could not be parsed, name the config file that was requested but not found or not
  readable, and reject a provider/endpoint URL without an `http`/`https` scheme instead of
  building requests from a relative URL.
- reproducible-by: `SEARCH_CONFIG_FILE=/tmp/does-not-exist SEARXNG_BASE_URL=searx.example.com SEARCH_MAX_RESULTS=lots SEARCH_LOG_LEVEL=verbose ./SwiftWebSearchMCP`
  → stderr shows no complaint about the file or the values, reports `configured=searxng`
  and `log_level=info`, and a later `web_search` fails with "SearXNG network failure: the
  transport rejected the request URL" rather than explaining the missing scheme.
- confidence: certain

#### L7-2 — Ctrl-C (or SIGTERM) leaves the dashboard's terminal in raw mode with the cursor hidden, and the Ctrl-C key branch is unreachable
- severity: S2
- unit: `MCPSMonitor` + `Monitor/Terminal.swift`
- file:line: `Sources/WebSearchCore/Monitor/Terminal.swift:156-157`, `:165-171`, `:187-189`; `Sources/MCPSMonitor/main.swift:508`, `:571-574`
- category: bug
- evidence: `KeyReader` claims crash safety in its doc comment — "`raw` is dropped when the
  process exits so a crash cannot leave the user's shell unusable" — but the only restore
  paths are the explicit `keyReader?.restore()` at `main.swift:574` and `deinit`, neither
  of which runs when a signal terminates the process. At the same time the raw termios
  clears only `ICANON | ECHO`, leaving `ISIG` set:
  ```swift
  raw.c_lflag &= ~tcflag_t(ICANON | ECHO)
  ```
  so Ctrl-C is delivered as `SIGINT` (default action: terminate) and never reaches the
  handler's Ctrl-C case at `main.swift:508` (`case "q", "Q", "\u{03}"`), which is therefore
  dead in a real terminal. `draw()` also hid the cursor (`Terminal.hideCursor`,
  `main.swift:484`), and that is not undone either. The result of the ordinary "press
  Ctrl-C to get out" path is a shell with echo and canonical mode off and an invisible
  cursor, recoverable only with `reset`/`stty sane` — exactly the state the comment says is
  impossible. `SIGTERM` has the same effect, and `keyReader?.restore()` after the loop does
  not help because the loop never exits.
- expected-correct: clear `ISIG` so Ctrl-C arrives as a byte (making the existing branch
  live), and/or install a `SIGINT`/`SIGTERM` handler that restores termios, shows the
  cursor and exits; either way a crash or a signal must not leave the tty raw.
- reproducible-by: run `mcps-mon` in a terminal and press Ctrl-C, then `stty -a` in the
  recovered shell (echo/canonical are off); `scripts/monitor_tty_smoke.py` does not cover
  this — it sends `q`, not `\x03`.
- confidence: certain

#### L7-3 — The server has no graceful shutdown; in HTTP mode the intended stop path can never run
- severity: S3
- unit: `SwiftWebSearchMCP` — `main.swift`, `HTTPMCPHost.swift`
- file:line: `Sources/SwiftWebSearchMCP/main.swift:92-95`, `:137-142`; `Sources/SwiftWebSearchMCP/HTTPMCPHost.swift:107-112`
- category: incomplete
- evidence: no `signal`/`sigaction`/`DispatchSourceSignal` handler exists anywhere in
  `Sources/` (`grep -rn "signal\|SIGTERM\|SIGINT" Sources/` finds only prose comments), so
  `SIGTERM`/`SIGINT` terminate the process at the default disposition. The only clean path
  is:
  ```swift
  await server.waitUntilCompleted()
  await shutdown(server: server, host: host)   // -> host.stop(): close channel, shutdownGracefully
  ```
  but for the stateful HTTP transport `waitUntilCompleted()` awaits the SDK's message loop,
  which iterates `connection.receive()` — an `AsyncThrowingStream` whose continuation is
  only finished by `terminate()`/`disconnect()` (SDK
  `Sources/MCP/Base/Transports/HTTPServer/StatefulHTTPServerTransport.swift:131`,
  `:157`). Nothing in this repository calls `transport.disconnect()`/`server.stop()` before
  awaiting, so the loop never finishes and `shutdown(server:host:)` — including
  `channel.close()` and `group.shutdownGracefully()` — is unreachable in normal operation.
  Every restart (reverse proxy reload, `launchctl kickstart`, `docker stop`) therefore
  drops in-flight MCP requests without draining and never releases the listener cleanly.
- expected-correct: handle `SIGTERM`/`SIGINT` (a `DispatchSourceSignal` task), then
  `await shutdown(server:host:)` and exit 0, so the listener closes, the event loop group
  shuts down and in-flight work is given a bounded drain.
- reproducible-by: run `SwiftWebSearchMCP --transport http --port 8080`, send `SIGTERM`,
  and observe the process dies without the "MCP server stopped" line or any
  `HTTPMCPHost.stop()` effect; a client mid-`tools/call` gets a reset connection.
- confidence: likely

#### L7-4 — The loopback-origin check accepts any host whose DNS name starts with `127.`
- severity: S3
- unit: `SwiftWebSearchMCP/HTTPMCPHost.swift`
- file:line: `Sources/SwiftWebSearchMCP/HTTPMCPHost.swift:445-449` (used at `:304-313`)
- category: bug
- evidence:
  ```swift
  private static func isLoopbackOrigin(_ origin: String) -> Bool {
      guard let url = URL(string: origin), let host = url.host() else { return false }
      return host == "127.0.0.1" || host == "::1" || host == "localhost"
          || host.hasPrefix("127.")
  }
  ```
  The prefix arm was presumably meant for the rest of `127.0.0.0/8`, but it matches a
  registrable name: `URL(string: "http://127.0.0.1.evil.com").host()` is
  `"127.0.0.1.evil.com"`, so a page served from that host passes the check that the code
  comment says stops "a browser page from driving the server". Practical impact is limited
  because the endpoint also requires `Content-Type: application/json` and
  `Accept: text/event-stream`, which forces a CORS preflight that this server answers with
  405 and no CORS headers, so a browser cannot reach the handler cross-origin regardless —
  which is why this is S3 and not higher.
- expected-correct: compare the parsed host as an address (`IPv4Address`/`inet_pton`) and
  accept only `127.0.0.0/8` literals, `::1` or exactly `localhost`, rather than
  prefix-matching the textual host.
- reproducible-by: `curl -H 'Origin: http://127.0.0.1.evil.com' -H 'Content-Type: application/json' -H 'Accept: application/json, text/event-stream' -X POST -d '{}' http://127.0.0.1:8080/mcp`
  reaches the SDK (session/validation error) instead of the 403 the same request with
  `Origin: https://evil.example.com` receives.
- confidence: certain

#### L7-14 — `Log.escape` leaves C0 control characters (including ESC) intact, so a logged query can drive the operator's terminal
- severity: S3
- unit: `WebSearchCore/Support/Logging.swift`
- file:line: `Sources/WebSearchCore/Support/Logging.swift:87-89`, `:109-123`
- category: unsafe
- evidence: the helper's stated goal is "Escape a value so a single log line stays a single
  line", but it handles only `\\`, `"`, `\n`, `\r` and `\t`:
  ```swift
  case "\\": escaped += "\\\\"
  case "\"": escaped += "\\\""
  case "\n": escaped += "\\n"
  case "\r": escaped += "\\r"
  case "\t": escaped += "\\t"
  default: escaped.append(character)
  ```
  With `SEARCH_LOG_QUERIES=true`, `queryDescription(_:)` returns the query verbatim (`:87-89`),
  so a query containing `ESC [` sequences reaches stderr unescaped and is interpreted by
  the terminal — log injection / OSC-style output manipulation on the operator's console.
  The default hashing means the ordinary configuration is not exposed.
- expected-correct: escape (or strip) every control scalar below `0x20` and `0x7F` in
  `escape(_:)`, e.g. `\u{1B}` → `\\e`, so no log value can emit terminal control.
- reproducible-by: `SEARCH_LOG_QUERIES=true` and call `web_search` with a query containing
  `\u{1B}[2J`; the escape arrives raw in the stderr line (a unit test over
  `Log.escape("\u{1B}[31m")` shows it unchanged).
- confidence: certain
