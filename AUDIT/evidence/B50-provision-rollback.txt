# B50 — provisioning destroyed the working instance before its replacement was proven on the production port

Platform: arm64 macOS · bash 3.2 · shellcheck 0.11.0 · branch `audit/2026-09-13`

## The residue is real, and the canary does not close it

The finding is correct as written. The ordering in the pre-fix tree was:

```bash
docker rm -f mcps-searxng >/dev/null 2>&1
docker run -d ... -p "${SEARXNG_PORT}:8080" ... || fail "docker run failed; ..."
wait_for_json "${SEARXNG_PORT}" || fail "searxng did not answer JSON on port ${SEARXNG_PORT}"
```

Everything the canary proves, it proves on `127.0.0.1:${SEARXNG_CANARY_PORT}` with a
`-p 127.0.0.1:<spare>:8080` binding. The production container is created with a different
binding — `-p "${SEARXNG_PORT}:8080"`, on all interfaces — and that binding is the one that
fails when another process already holds `${SEARXNG_PORT}`, or when the container comes up but
never answers JSON there. The canary cannot see either. By the time those two failures can
occur the old container has been `rm -f`-ed, and the script keeps no compose file, tag, or
retained image for it on the node, so `fail` leaves the node serving nothing with no in-place
recovery. This is narrower than the pre-audit defect (which removed the container before the
image was validated at all) and the canary is what narrows it; the port-binding gap and the
missing rollback are genuine.

One correction to the *shape* the finding's notes suggest. The note proposes starting the
replacement "under a temporary name/port". A temporary **port** would repeat the canary's
mistake — it would not exercise `-p ${SEARXNG_PORT}:8080`. And a temporary **name** on the
production port cannot coexist with the old container, which still holds that port. The only
shape that actually proves the production binding is to vacate the port reversibly: `docker
rename` the old container aside, **stop** it (which frees the port but keeps the container's
configuration), run the replacement under the canonical name and production port, and remove
the old container only once the replacement has answered. That is what is implemented, plus the
`docker rename`-aside rollback and the previous digest in the READY output the note asks for.

## The fix

The swap is extracted into functions so it can be exercised without provisioning a node, the
same convention as `install_secret_key` (B17/B49) and `load_pinned_image`/`make_provision_tmp`
(B86). `deploy/provision-node.sh:394-478`:

```bash
PREVIOUS_CONTAINER_NAME="mcps-searxng-previous"
# Non-empty only while a previous container is aside awaiting proof or rollback, so a first
# provisioning run — which has nothing to restore — takes the same failure paths as before.
SWAP_PREVIOUS_NAME=""
# The digest the previous container ran, kept for the READY output so a rollback after this
# run is one command rather than an archaeology exercise (ledger B50).
PREVIOUS_IMAGE=""

restore_previous_instance() {
    [ -n "${SWAP_PREVIOUS_NAME}" ] || return 0
    docker rm -f mcps-searxng >/dev/null 2>&1
    docker rename "${SWAP_PREVIOUS_NAME}" mcps-searxng \
        || say "could not rename ${SWAP_PREVIOUS_NAME} back to mcps-searxng"
    docker start mcps-searxng > "${PROVISION_TMP}/docker-restore.log" 2>&1 \
        || say "could not restart mcps-searxng; see ${PROVISION_TMP}/docker-restore.log"
    say "restored the previous mcps-searxng container"
    SWAP_PREVIOUS_NAME=""
}

swap_fail() {
    restore_previous_instance
    fail "$*"
}

replace_running_instance() {
    if docker container inspect mcps-searxng >/dev/null 2>&1; then
        PREVIOUS_IMAGE="$(docker inspect --format '{{.Config.Image}}' mcps-searxng 2>/dev/null)"
        # Renamed aside, never removed: this container is the only record of how the node was
        # serving, and it is what a rollback restores (ledger B50).
        docker rm -f "${PREVIOUS_CONTAINER_NAME}" >/dev/null 2>&1
        docker rename mcps-searxng "${PREVIOUS_CONTAINER_NAME}" \
            || fail "could not rename the running container aside; it is still serving on port ${SEARXNG_PORT}"
        SWAP_PREVIOUS_NAME="${PREVIOUS_CONTAINER_NAME}"
        # `stop` frees the production port without destroying the configuration; `--restart
        # unless-stopped` will not bring it back while it is stopped by hand.
        docker stop "${PREVIOUS_CONTAINER_NAME}" > "${PROVISION_TMP}/docker-stop.log" 2>&1 \
            || swap_fail "could not stop the previous container; see ${PROVISION_TMP}/docker-stop.log"
    fi

    docker rm -f mcps-searxng >/dev/null 2>&1

    docker run -d \
        --name mcps-searxng \
        --restart unless-stopped \
        -p "${SEARXNG_PORT}:8080" \
        -v "${INSTALL_DIR}/searxng/settings.yml:/etc/searxng/settings.yml:ro" \
        "${SEARXNG_IMAGE}" > "${PROVISION_TMP}/docker-run.log" 2>&1 \
        || swap_fail "docker run failed; see ${PROVISION_TMP}/docker-run.log"

    say "waiting for searxng to answer JSON"
    wait_for_json "${SEARXNG_PORT}" || swap_fail "searxng did not answer JSON on port ${SEARXNG_PORT}"

    # Proven on the production port: only now is the previous container expendable.
    if [ -n "${SWAP_PREVIOUS_NAME}" ]; then
        docker rm -f "${SWAP_PREVIOUS_NAME}" >/dev/null 2>&1
        SWAP_PREVIOUS_NAME=""
    fi
}

replace_running_instance
```

Why each piece is there:

* **`rename` + `stop`, never `rm`, before the proof.** `rm` destroys the container
  configuration — the only record on the node of how the instance was running. `stop` frees
  `${SEARXNG_PORT}` and leaves that configuration intact, so it can be started again. Because
  the old container is stopped by hand, `--restart unless-stopped` does not resurrect it while
  the swap is in progress.
* **`swap_fail` on every fallible mutation.** `docker stop`, `docker run` and the production
  health wait all route their failure through `swap_fail`, which restores the previous
  container and then exits with the same message the failure produced before. A first
  provisioning run has `SWAP_PREVIOUS_NAME` empty, so `restore_previous_instance` is a no-op
  and the behaviour is unchanged.
* **The old container is removed only after `wait_for_json "${SEARXNG_PORT}"` succeeds.** This
  is the point of the whole change.
* **`PREVIOUS_IMAGE` in the READY output** (`deploy/provision-node.sh:536-541`), printed only
  when it differs from the new pin, so a rollback is one command.

```bash
if [ -n "${PREVIOUS_IMAGE}" ] && [ "${PREVIOUS_IMAGE}" != "${SEARXNG_IMAGE}" ]; then
    say "previous image digest (rollback): ${PREVIOUS_IMAGE}"
fi
```

## The harness

`$HOME/Library/Caches/MCPSearch/check-b50.sh`, outside the repository, in the shape of the B86
and B49 harnesses. It extracts the three functions **and the three name constants** verbatim
from the working tree for `fixed` and from `git show <ref>:deploy/provision-node.sh` for
`unfixed`, stubs `fail`/`say`/`wait_for_json`/`docker`, and drives six cases.

* `wait_for_json` is stubbed (`B50_HEALTH=ok|bad`) because the real one polls for up to 60s;
  its verdict is the input the swap consumes, not its timing.
* The `docker` stub models only what the swap can be judged on: `$B50_STATE/<name>` is the
  container's configuration (the image it was created from) and `$B50_STATE/running/<name>` is
  "up". `rm` deletes the configuration, `stop` clears only the running marker, `rename` moves
  both, `start` restores the marker, and `run` creates both (or fails with `B50_RUN_STATUS`).
  That asymmetry is exactly the difference between `rm -f` and `stop`.
* The observation is what the node is left doing: `previous-running` (the canonical container
  holds the old image and is up), `new-running` (it holds the pin and is up), `none`,
  `aside-only`, or `stopped`.
* The pre-fix block is extracted **verbatim** (no edit was needed — post-B86 it already writes
  its log under `${PROVISION_TMP}`, which the harness points at a fixture directory, so nothing
  writes to `/tmp`). Verified:

```
$ git show HEAD:deploy/provision-node.sh | sed -n '394,408p' > head-block.txt
$ diff $HOME/Library/Caches/MCPSearch/B50/body.sh head-block.txt
IDENTICAL to HEAD:394-408
```

The same check for the fixed side: each of `restore_previous_instance`, `swap_fail` and
`replace_running_instance` in the harness's extracted functions is byte-identical to the same
function in `deploy/provision-node.sh` (`diff` per function: VERBATIM).

* `run-fail-after-rm`, the port-conflict / `docker run` error: the old container was removed
  and the replacement never started, so the node is left with **no container at all**.
* `health-fail-after-rm`, the case the canary cannot see: the old container is gone and the
  **unproven new one holds the production name and port**; it never answered JSON on
  `${SEARXNG_PORT}`. The instance is not serving and there is nothing to roll back to.
* `stop-fail` is the reversible step the fix adds; the pre-fix code has no such
  step, so it replaces the instance regardless.

`success`, `first-run-fail` and `first-run-success` pass on both trees — they are controls, not
differences: a successful swap serves the new instance, and a first provisioning run has
nothing to restore either way.

after a rollback is not "some container is up" — it is the old image running.

## Not executed, and what is unverified

Provisioning was **not** run, and no real container was started, stopped, renamed or removed:
the `docker` CLI is stubbed and first on `PATH` for every case. The live instance on the node was
not touched. `swift build`/`swift test` were not run.

The harness models the daemon, so the following are **unverified** and not claimed:

* That this Docker version's `docker rename` on a running container, followed by `docker stop`,
  then `docker start` on the renamed-back container, behaves exactly as the stub models. These
  are standard, long-standing Docker behaviours; they were not exercised against the node's
  daemon.
* A `docker stop` that fails by timing out (the container is still running) or after the
  container already exited. The configuration is preserved either way and `docker start` is
  attempted, but the exact resulting state was not measured.
* If the script is killed with an uncatchable signal between the `stop` and the rollback, the
  old container is left stopped and renamed aside rather than restored. `fail` is the only
  failure path this fix controls, and it always rolls back; the EXIT trap was deliberately left
  as B86's `cleanup_provision_tmp` so its behaviour and harness stay intact. This residue is
  narrower than the original (the configuration still exists on the node and is one `docker
  rename` + `docker start` away) but it is not zero.
* If a previous run left both `mcps-searxng` (a replacement that failed after the port was
  taken) and `mcps-searxng-previous` (the old container) on the node, a re-run removes the
  stale aside name before renaming, so the old configuration can be lost. The rollback in the
  fix is what prevents that pair from arising in normal operation; it was not tested against a
  node left in that state by an older version of the script.
