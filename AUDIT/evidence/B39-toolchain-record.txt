# B39 — CI did not pin the Swift toolchain, and did not say which one ran

Host: this Mac (arm64, macOS 26.6.2) · branch audit/2026-09-13

## What was wrong

The job runs on `macos-26` and then selects the *newest* Xcode present on the image, with the only
constraint being the `>= 6.3` assertion (B22). Nothing recorded which compiler actually ran, so
"tested with Swift 6.3" was an assertion about the image's contents at that moment rather than about
the run. The manifest demands `swift-tools-version: 6.3`, so a toolchain drift is a real (if slow)
risk: an image update can change the compiler under a green build without any commit.

## The decision

The finding allows either an explicit pin or an explicit statement that reproducibility is not
guaranteed *plus* the actual version in the run summary. The second was chosen:

* **A hard `DEVELOPER_DIR=/Applications/Xcode_<n>.app` pin fails for the wrong reason.** The runner
  image rotates its Xcode installs, so a pin turns "GitHub updated the image" into a red build
  unrelated to the change under test — and the workflow already selects the newest Xcode for exactly
  that reason. The floor is what protects the manifest, and B22 made the floor fail hard when it
  cannot be read.
* **Recording makes the claim checkable.** Every run now publishes the exact `swift --version` in its
  summary, so "green on the branch with Swift 6.3.3" is a fact about a named run rather than an
  assumption about `macos-26`.

The reasoning lives in the workflow next to the code, so the next reader sees the trade-off rather
than an unexplained absence of a pin.

## Verification

The step's `run` block was extracted from the workflow with PyYAML and replayed with a stubbed
`swift` and a `GITHUB_STEP_SUMMARY` file (the two things the runner provides):

```
$ PATH=<stub>:... GITHUB_STEP_SUMMARY=<file> bash <extracted step>
Apple Swift version 6.3.3 (swift-6.3-RELEASE)
Swift 6.3 satisfies swift-tools-version 6.3
step exit: 0

$ cat <file>
### Swift toolchain

```
Apple Swift version 6.3.3 (swift-6.3-RELEASE)
```
```

The workflow still parses (12 steps in `build-and-test`), and the next dispatched run publishes the
toolchain it really used.
