# B88 — the declared per-host DNS cache did not exist, and a redirect hop resolved twice

Host: this Mac (arm64, macOS 26.6.2, Swift 6.3.3) · branch audit/2026-09-13

## What was wrong

`URLPolicy` declared a cache it did not have:

```swift
// URLPolicy.swift, before
/// Per-host cached DNS results, so a redirect chain does not re-resolve.
private let resolver: any DNSResolver
```

`resolver` is a plain stored property and `SystemDNSResolver.resolve` shells out to
`getaddrinfo` on every call, so the comment described work the code never did. The only DNS
memo in the fetch path was in the reader's head.

The duplicate work was real. `DirectHTTPFetcher` validates each hop twice — once pre-emptively
against the `Location` target and again at the top of the loop — so a one-hop redirect cost
three lookups for two hosts and a chain that returns to an earlier host paid again every time.

## The fix

The claim is now true, and its scope is the part that matters for SSRF. `URLPolicy.validate`
keeps its public signature and delegates to a new internal overload that takes a cache:

```swift
public func validate(_ url: URL) async -> Decision {
    // No cache: a caller outside a fetch loop gets a fresh answer every time, which is
    // the behaviour `DirectHTTPFetcher` relies on across requests (ledger B88).
    await validate(url, cache: nil)
}

func validate(_ url: URL, cache: DNSAnswerCache?) async -> Decision {
    ...
    let addresses: [IPAddress]
    if let cached = cache?.addresses(for: host) {
        addresses = cached
    } else {
        do {
            addresses = try await resolver.resolve(host: host)
        } catch {
            return .allow
        }
        cache?.store(addresses, for: host)
    }
    for address in addresses {
        let decision = validate(address: address, host: host)
        if !decision.allowed { return decision }
    }
    return .allow
}
```

`DirectHTTPFetcher.fetch` creates one `DNSAnswerCache` per call and passes it to both
validations of every hop:

```swift
let resolutions = DNSAnswerCache()
...
let decision = await policy.validate(currentURL, cache: resolutions)
...
let hopDecision = await policy.validate(nextURL, cache: resolutions)
```

No public signature changed: `validate(_:)` is byte-for-byte the same call for every existing
caller, and the cache overload is internal.

## The invariant: per-hop re-validation is not weakened

Three properties keep the SSRF boundary exactly where it was.

1. **The cache stores addresses, never decisions.** Every validation still runs the full
   `validate(address:host:)` classification over every address, cached or fresh, so a name
   that answers with `10.0.0.5` is denied on every validation in the chain. The cache cannot
   return `.allow` on its own.
2. **An unseen host is resolved before it is judged.** The memo is keyed by host, and only a
   successful lookup is stored; a miss falls through to `resolver.resolve`. The cache
   therefore cannot skip a host that was never checked.
3. **The memo dies with the fetch.** It is created inside `fetch` and dropped on return, so
   two requests never share an answer. A process-lifetime cache would have weakened the
   policy's DNS-rebinding bound in the dangerous direction — a name that resolved to public
   space a moment ago would be re-validated against that stale answer while `URLSession`
   connects to whatever it resolves to now. The public `validate(_:)` path is uncached for
   the same reason.

A resolution *failure* is deliberately not memoised: the policy lets a failing lookup through
so the fetch fails with a real network error, and storing "no addresses" would pin a transient
resolver failure for the rest of the fetch.

The pre-emptive hop check is kept as well as the loop-top re-check. The finding offered
"delete the claim" or "implement the cache"; the cache removes the duplicate *resolution*
without removing the second *decision*, which was the safe half of the redundancy.

## The tests

Four tests in `Tests/WebSearchCoreTests/URLPolicyTests.swift`, against a new
`CountingDNSResolver` that records every host it is asked for, so the contract is asserted
rather than timed:

* `testOneFetchAsksForAHostOnceHoweverManyHopsAreValidated` — two validations of one host
  through one cache produce exactly one lookup.
* `testAnUnseenHostIsStillResolvedThroughTheCache` — a second host is resolved once, and a
  repeat of the first adds nothing.
* `testACachedPrivateAnswerIsDeniedOnEveryValidation` — the cached `10.0.0.5` is still
  classified, so the second validation is denied with the "private" reason.
* `testAValidationWithoutAFetchCacheResolvesEveryTime` — the public path is uncached, which is
  the cross-request re-resolution.

## Noted, not pinned

The *fetch-level* lookup count is not observable end to end: the loopback fixture in
`FetchRedirectTests` is an IP literal, and the private-network opt-in that makes it reachable
short-circuits address resolution by design, so no in-process redirect chain can be made to
consult a counting resolver. The memo contract is therefore pinned where the existing
redirect tests pin the address-level hop check too — against the exact `URLPolicy` object the
loop calls, with the same cache object the loop would pass. The wiring itself (one cache per
`fetch`) is a two-line change at two call sites and is visible in the diff above.
