Host: `node1 (arm64, macOS 26.6.2)` · branch `audit/2026-09-13` · Swift 6.3.3

## Premise check: still open

Grepped before writing: `markupDepthExceeded` appears in tests only at the three pre-existing
assertions in `MarkupDepthTests.swift`, and no other test file mentions `MarkupDepth` or
`exceedsLimit` (only a comment in `HTMLExtractorTests`). The four gaps the finding names were all

1. `skipRawText`'s unterminated branch — every raw-text fixture closed its element.
2. the `Array(html.utf8)[...]` path — no test called `scan` on a slice.
3. `markupDepthExceeded`'s `category`/`safeDescription` — only the case value was asserted.
4. the `web_open` end-to-end contract — nothing reached it at all.

## What was added (five test methods, no production change)

| Test | Pins |
| --- | --- |
| `testUnterminatedRawTextSwallowsTheRestOfTheDocument` | an unclosed `<script>` holds no elements, so 20 000 `<div>`s inside it are not nesting |
| `testUnterminatedRawTextIsSkippedRatherThanScanned` | exactly the limit in real elements, then an unclosed `<style>` full of markup, is still accepted |
| `testScanOverANonContiguousByteViewAgreesWithTheContiguousPath` | `scan` honours a slice's own `startIndex` and `endIndex` |
| `testMarkupDepthExceededProjectsOntoTheSharedTaxonomy` | `category == .malformedResponse`, `provider == nil`, exact `safeDescription`, and that the limit is carried through |
| `testWebOpenOnADeeplyNestedPageIsAToolError` | a real stdio session gets `isError == true` and the model-visible sentence for a 20 000-deep page |

The raw-text fixtures use 20 000 levels deliberately: they would trip the 512 limit immediately if
the content were scanned, so there is no small-input way for the skip to pass by accident.

## One honest limit on the second assertion

The `withContiguousStorageIfAvailable` fallback in `exceedsLimit` cannot be reached from a test on
this platform: a native `String` built any way I tried hands out contiguous UTF-8, so the `else`
branch does not execute under test. The test therefore pins the *slice semantics that branch
depends on* (`scan` over an `ArraySlice` with a non-zero `startIndex`) rather than claiming to
execute the fallback. This is stated rather than papered over; the fallback lines remain uncovered
by measurement, and a coverage report naming them is the honest record.

## Deviation

The expected-correct asked for "a direct `scan(ArraySlice(...))` test built from a non-contiguous
UTF-8 view". A non-contiguous view is not constructible here, so the test calls `scan` with the
slice type the fallback builds instead, and the limitation is documented above. No production code
changed.
