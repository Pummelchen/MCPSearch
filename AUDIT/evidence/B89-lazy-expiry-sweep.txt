# B89 — `SearchCache.pruneExpired` rebuilt the whole dictionary on every access

Host: this Mac (arm64, macOS 26.6.2, Swift 6.3.3) · branch audit/2026-09-13

## What was wrong

```swift
// SearchCache.swift, before
public func get(_ key: Key) -> SearchResponse? {
    pruneExpired()
    ...
}
public func stats() -> Stats {
    pruneExpired()
    ...
}
private func pruneExpired() {
    let now = clock.now()
    storage = storage.filter { now.timeIntervalSince($0.value.storedAt) < $0.value.ttl.seconds }
}
```

Every `get` — that is, every search — allocated a fresh dictionary and re-hashed every live
entry, even when nothing had expired. `store` and `stats` did the same.

## The fix

Expiry is now an absolute deadline on the entry and an earliest-deadline watermark on the
cache, so a sweep runs only when something is actually due:

```swift
private struct Entry {
    let response: SearchResponse
    let storedAt: Date
    let expiresAt: Date
}

/// The earliest deadline any stored entry has.
private var nextExpiry: Date?
```

* `get` no longer sweeps at all. It looks the requested key up directly and removes it on the
  spot if its deadline has passed — the branch the old code already had.
* `store` inserts, lowers `nextExpiry` if the new entry is earlier, then sweeps and enforces
  the capacity bound, in the same order as before.
* `stats` sweeps (when due) and reports the same numbers.
* `sweepExpired(now:)` removes expired entries **in place** instead of assigning a filtered
  copy, and recomputes `nextExpiry` from the survivors.

The public API is unchanged.

## The invariant: the observable semantics are identical

`nextExpiry` is only ever lowered by a `store` and recomputed exactly by a sweep. Entries are
only ever removed, never given a new deadline, so the watermark can be stale-early (the entry
it named was read, swept or evicted) but never stale-late. By induction it is always at most
the earliest deadline in `storage`:

* a store lowers it to `min(old, new)`;
* removing an entry can only raise the minimum of the remaining set;
* a sweep sets it to exactly that minimum.

Therefore `nextExpiry > now` implies no stored entry is expired, and skipping the sweep when
the guard is false changes nothing; `nextExpiry <= now` implies at least one entry is expired,
so the sweep is never skipped when it matters — after it, every survivor has a deadline in the
future.

What that preserves, item by item:

* **`get` results and the hit/miss counters** — the requested key is still judged by its own
  deadline, which is now the same value the sweep compares (`expiresAt`), so the boundary
  cannot disagree between the two paths. An expired key is removed and misses.
* **`stats().entries` still counts live entries only** — an expired entry anywhere in
  `storage` makes the sweep due before the count is taken.
* **The capacity bound** — `store` still sweeps before comparing against `capacity`, so
  expired entries never hold capacity hostage, and the eviction order (`storedAt`, then
  `Dictionary.sorted`) is untouched.
* **"Successful responses only"** — the `ttl.seconds > 0, response.hasUsableResults` guard and
  its position are unchanged.

## The tests

Two tests in `SearchCacheTests` (`Tests/WebSearchCoreTests/FusionAndReliabilityTests.swift`),
driven by the existing `TestClock` so nothing is timed:

* `testStatsCountOnlyLiveEntries` — one short-TTL and one long-TTL entry, clock advanced past
  the short one: `stats().entries == 1`, the expired key reads `nil`, the live one still hits.
* `testExpiredEntriesDoNotConsumeCapacity` — a cache at `capacity: 8` filled with entries whose
  TTL lapses, then one long-lived store: `stats().entries == 1` and the live key is present,
  so the eight expired entries neither count nor evict it.

## Proof the tests can fail (two mutations)

The finding is a complexity claim, so the honest first mutation is the literal one: **restore
the pre-fix `SearchCache.swift`** (`git show HEAD:…`) with the new tests in place. Both tests
**pass**, which is the evidence that the fast path really does preserve the old observable
semantics rather than merely claiming to:


M2 — with the new implementation back in place, **remove the two `sweepExpired` call sites**

## Noted, not changed

`evictOldest` still sorts the whole dictionary on overflow. That is O(capacity log capacity)
only on the write that overflows, not on every read, and the finding names `pruneExpired`; a
second ordering index would be a larger change than the hot-path defect it would remove.
