# B116 — a local throttle that cleared between two reads was reported as a hard skip

Host: this Mac (arm64, macOS 26.6.2, Swift 6.3.3) · branch audit/2026-09-13

## What was wrong

`swift test` failed roughly one run in twenty with

```
Tests/WebSearchCoreTests/StdioServerTests.swift:1087: error: -[WebSearchCoreTests.StdioServerTests testToolArgumentClampsAreEnforced] : XCTUnwrap failed: expected non-nil value of type "Array<Dictionary<String, Any>>"
```

`SearchOrchestrator.authorizationAfterBoundedWait` reads the local rate limiter twice: once to
authorise the request, and — only when that is refused as `rateLimited` — once more to decide
whether the wait is worth the search budget:

```swift
guard let denial = await health.authorize(id) else { return nil }
guard allowWaiting, denial.category == .rateLimited,
    let wait = await health.localWait(for: id),
    wait <= SearchOrchestrator.maximumLocalWait,
    wait.milliseconds
        <= Int(Double(budget.milliseconds) * SearchOrchestrator.localWaitBudgetShare)
else {
    return denial
}
```

`ProviderHealth.localWait(for:)` delegates to `RateLimiter.timeUntilAvailable()`, which reports
*"available now"* as `nil`:

```swift
public func timeUntilAvailable() -> Duration? {
    refill()
    if tokens >= 1 {
        if let minimumInterval = policy.minimumInterval, let lastAcquire {
            let elapsed = clock.now().timeIntervalSince(lastAcquire)
            let remaining = minimumInterval.seconds - elapsed
            if remaining > 0 { return .milliseconds(Int(remaining * 1000)) }
        }
        return nil          // <-- "available now"
    }
    ...
}
```

`authorize` denies while `elapsed < minimumInterval.seconds`. The clock can cross the interval
between that read and the `localWait` read, at which point `timeUntilAvailable()` correctly
reports "available now" as `nil` — and `guard let wait` read `nil` as "cannot wait", returned the
stale denial, and recorded the provider in `skippedLocally`. Nothing is attempted, so a
single-provider search throws `temporarilyUnavailable` and the tool call has no structured
content: exactly the observed `XCTUnwrap` failure.

The boundary is real but narrow, which is why it fired only when the two reads straddled the
interval. One detail the original report did not spell out: `ProviderHealth.authorize` itself
calls `timeUntilAvailable()` to put a "Retry in about N ms" suffix on the denial message, so each
refused `authorize` is four clock reads (refill + interval check, then refill + interval check),
not one — the window is wider than a single read, but it is still a boundary that a real clock
crosses intermittently.

## The two defects

| # | Where | Defect | Effect |
|---|-------|--------|--------|
| 1 | `SearchOrchestrator.authorizationAfterBoundedWait` | A `nil` wait estimate — "the token/interval is available now" — was treated as "cannot wait" and returned the stale denial. | The provider was skipped and a search that had a usable provider failed empty (the `XCTUnwrap` flake). |
| 2 | `RateLimiter.timeUntilAvailable`, min-interval branch | `Int(remaining * 1000)` truncates, so the estimate could be up to 1 ms short and a sub-millisecond remainder became `.milliseconds(0)`; the token branch a few lines below already rounds up. | A caller that slept exactly the reported wait could wake a hair before the threshold and be denied again on the single retry. |

## The fix

Defect 1: split the combined guard. A `nil` estimate is not a reason to give up — it means the
throttle has already cleared — so `authorize` is retried once. Only a non-nil estimate that
exceeds either cap returns the denial. The bounded-wait branch below is untouched.

```
$ git diff -- Sources/WebSearchCore/Search/SearchOrchestrator.swift
@@ -454,9 +454,15 @@ public actor SearchOrchestrator {
         allowWaiting: Bool
     ) async -> ProviderFailure? {
         guard let denial = await health.authorize(id) else { return nil }
-        guard allowWaiting, denial.category == .rateLimited,
-            let wait = await health.localWait(for: id),
-            wait <= SearchOrchestrator.maximumLocalWait,
+        guard allowWaiting, denial.category == .rateLimited else { return denial }
+        // `localWait` reports an already-cleared throttle as nil, and the throttle can clear in
+        // the microseconds between `authorize` and this second read: the denial is then stale and
+        // the request it refused is allowed. Retrying `authorize` here is what keeps that boundary
+        // race from turning a search that had a usable provider into an empty one (ledger B116).
+        guard let wait = await health.localWait(for: id) else {
+            return await health.authorize(id)
+        }
+        guard wait <= SearchOrchestrator.maximumLocalWait,
             wait.milliseconds
                 <= Int(Double(budget.milliseconds) * SearchOrchestrator.localWaitBudgetShare)
         else {
```

Defect 2: round the min-interval remainder up, matching the token branch, and let a non-positive
remainder fall through to the existing `return nil`.

```
$ git diff -- Sources/WebSearchCore/Search/RateLimiter.swift
@@ -97,7 +97,12 @@ public actor RateLimiter {
             if let minimumInterval = policy.minimumInterval, let lastAcquire {
                 let elapsed = clock.now().timeIntervalSince(lastAcquire)
                 let remaining = minimumInterval.seconds - elapsed
-                if remaining > 0 { return .milliseconds(Int(remaining * 1000)) }
+                // Rounded up, like the token branch below: a truncated estimate can be up to a
+                // millisecond short, so a caller that sleeps exactly what it was told can wake a
+                // hair before the threshold and be denied again. A remainder that rounds to zero
+                // is "available now", not a zero-length wait (ledger B116).
+                let milliseconds = Int((remaining * 1000).rounded(.up))
+                if milliseconds > 0 { return .milliseconds(milliseconds) }
             }
             return nil
         }
```

No public signature changes; `tryAcquire` is untouched.

## The deterministic tests

`TestClock` does not move on its own, so it cannot reproduce a race whose shape is "the clock
advanced between two reads of it". `Tests/WebSearchCoreTests/TestSupport.swift` gains a
`CreepingClock` that advances by a fixed step on **every** `now()` read. It is used by
`Tests/WebSearchCoreTests/LocalThrottleRaceTests.swift`:

* `testALocalThrottleThatClearsBetweenReadsStillReturnsResults` — one provider, a two-token
  bucket with a 1 ms-per-read clock and an 8 ms `minimumInterval`. After the priming acquire, the
  reads the search performs put the last-resort authorising read 7 ms behind the interval (deny)
  and the wait-estimating read 11 ms behind it (`localWait` returns `nil`). The search must return
  the provider's result; before the fix it throws `temporarilyUnavailable`.
* `testTimeUntilAvailableRoundsTheMinimumIntervalUp` — a 1 499.5 ms advance leaves a 0.5 ms
  remainder, so the returned wait must be `>=` the true remainder (never short) and greater than
  zero milliseconds.
* `testTimeUntilAvailableReturnsNilWhenTheMinimumIntervalHasElapsed` — a remainder of zero is
  "available now", so the wait is `nil`, never `.milliseconds(0)`.

gates, back to back, in addition to the gate run (33 full green runs in total). Every one
