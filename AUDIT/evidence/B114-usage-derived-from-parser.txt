# B114 — `usage` was hand-maintained and had drifted from the parser

Host: this Mac (arm64, macOS 26.6.2, Swift 6.3.3) · branch audit/2026-09-13

## What was wrong

`ServerOptions.usage` was a hand-written string listing five transport flags. The parser accepted
more than the text described:

* `--help` / `-h` (`parse` recognized both; neither appeared in the text),
* the `streamable-http` and `streamable_http` aliases for `--transport` (accepted, not mentioned),
* the `--flag=value` spelling (accepted for every value flag, not mentioned).

The guard that should have noticed was toothless:

```swift
// TransportConfigurationTests.swift, before
func testUsageDocumentsEveryFlag() {
    for flag in ["--transport", "--port", "--host", "--http-path", "--http-allowed-host"] {
        XCTAssertTrue(ServerOptions.usage.contains(flag), "usage text is missing \(flag)")
    }
}
```

A hand-written list checked against a hand-written string: the parser could grow a flag and the
test kept passing. A raw `contains` check is also weaker than it looks — `-h` is a substring of
`--http-allowed-host`, so even a fixed list would have blessed the short alias without the text
ever documenting it.

Separately, the empty-configuration warning named five variables
(`TAVILY_API_KEY`, `BRAVE_SEARCH_API_KEY`, `MOJEEK_API_KEY`, `EXA_API_KEY`, `SEARXNG_BASE_URL`)
and omitted `OPEN_WEB_SEARCH_URL`, `SEARCH_ENABLE_SCRAPERS` and `SEARCH_ENABLE_PARALLEL`.

## The fix

The flag names, their aliases, value placeholders and descriptions now live in one table,
`ServerOptions.Flag`, and the accepted `--transport` values in `ServerOptions.TransportName`.
`parse` dispatches on the table (`Flag.matching`, with `inlineValue` for the `=` spelling) and
`usage` is rendered from the same table, so a flag cannot be accepted without being documented or
documented without being accepted: the per-case `switch`es are exhaustive, and adding a case
forces an entry in every one.

```swift
// TransportConfiguration.swift, after (abridged)
enum Flag: CaseIterable {
    case help, transport, port, host, httpAllowedHost, httpPath

    var names: [String] { … }            // ["--help", "-h"], …
    var takesValue: Bool { … }
    var valuePlaceholder: String? { … }  // "stdio|http", "n", …
    var selectsHTTP: Bool { … }
    var documentedForm: String { … }     // "--port <n>" / "--help, -h"
    var documentation: [String] { … }

    static func matching(_ argument: String) -> Flag? { … }
    func inlineValue(in argument: String) -> String? { … }
}

enum TransportName: String, CaseIterable {
    case stdio, http
    case streamableHyphen = "streamable-http"
    case streamableUnderscore = "streamable_http"
}

public static let usage: String = renderUsage()
```

`renderUsage` lays out the `OPTIONS` column from `Flag.allCases`, derives the "Setting any of …"
sentence from the flags marked `selectsHTTP`, and takes the alias list from
`TransportName.allCases`. The generated text is:

```
OPTIONS
  --help, -h                  Print this usage and exit.
  --transport <stdio|http>    Transport to serve on: stdio, http, streamable-http, streamable_http.
                              Default: stdio.
  --port <n>                  HTTP port. Default: 8080
  --host <addr>               HTTP bind address. Default: 127.0.0.1
  --http-allowed-host <host>  Extra Host this server answers to, repeatable. Setting it
                              selects the HTTP transport, like the flags above.
  --http-path <path>          MCP endpoint path. Default: /mcp

Every flag that takes a value also accepts the --flag=value spelling, for example
--port=8080.

Setting any of --port, --host, --http-allowed-host or --http-path selects the HTTP transport,
so --transport http is optional. Combining one with an explicit --transport stdio is rejected
rather than silently resolved.
```

In `main.swift` the provider inventory became a table,
`providerAvailability: [(provider, variables, configured)]`, and the warning names the unique
variables from that table, so adding a provider cannot leave either message stale. No public
signature changed: `ServerOptions`, its `transport`/`wantsHelp`/`httpConfiguration` members,
`ServerOptions.parse`, `OptionError` and the `usage` global are all source-compatible.

## Tests

`testUsageDocumentsEveryFlagTheParserAccepts` iterates `Flag.allCases` (every `names` entry) and
`TransportName.allCases`, and matches whole whitespace tokens rather than substrings. Two more
tests are table-driven over the parser's own table:

* `testEveryDocumentedFlagIsAcceptedByTheParser` — every flag parses with a sample value;
* `testEveryValueFlagAcceptsBothSpellings` — `--flag value` and `--flag=value` select the same
  transport for every value flag.

`sampleValue(for:)` and `usageTokens()` are private test helpers; `sampleValue` switches
exhaustively without a `default`, so a new `Flag` case is a compile error until the test supplies
a value for it. `testMissingValuesAreRejected` was likewise changed from a hand-written list to
`Flag.allCases where flag.takesValue`.

A process-level test, `testEmptyConfigurationWarningNamesEveryProviderVariable`, starts the real
executable with the provider environment scrubbed and asserts the warning on stderr names all
eight provider-registering variables.

## Interaction with B113, and what was concluded

B113 and B114 both touch process startup, and the order they were done in matters to how each was
verified. B113 moved the argv parse and the `--help` arm above `AppConfiguration.load()`, which
made the help request independent of the environment; B114 then changed what `usage` *says* without
touching when it is produced. Doing B113 first meant a `--help` under a fatal `SEARCH_CONFIG_FILE`
could already reach the usage text, so the derived text could be observed and asserted through the
real executable rather than only through a unit call — the `--help` output quoted above is that
observation.

The two are otherwise cleanly separated: B113 owns *when* the command line is read, B114 owns
*what* it documents. B113's process tests assert the exit status, the presence of `USAGE` and the
absence of startup diagnostics, never the exact flag text, so they stayed green across the B114
rewrite (re-run in the 501-test suite above). B113's bad-flag path prints `ServerOptions.usage`
after its error line; B114 shortens and re-derives that text, but the error line and exit code are
unchanged, so the B113 assertion on `Unknown argument: --not-a-flag` is unaffected. Had B114 been
done first, B113's reorder would still have been required: a derived table does not change the fact
that loading configuration first pre-empts `--help`.

## Noted, not changed

* `--transport`'s invalid-value error still says `expected: "stdio or http"` while the usage now
  names the aliases. Changing it would alter an existing pinned assertion and a user-facing string
  beyond this task's expected-correct; the table is the single source for what is *accepted*, and
  the alias list is documented in `--help`. If the error text should list the aliases too, that is
  a separate, deliberate wording change.
* `MCPSMonitor`'s `Options.usage` has the same hand-maintained shape, but it is a different
  executable and its own task surface, so it was left alone.
* While this task was in progress another worker committed `audit(B117)` on the same branch. It
  touches only `scripts/mcp_smoke.py` and the ledger, so it does not interact with this change;
  every gate above was run on the frozen working tree, and the ledger was extended with the helper
  so both tasks' rows and counts are consistent.
