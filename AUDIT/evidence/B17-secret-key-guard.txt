# B17 — the secret-key substitution was the one unchecked mutation

Host: MacBook-AB.local (arm64, macOS 26.6.2) · branch audit/2026-09-13 · bash 3.2 (macOS)

## What was wrong

`provision-node.sh` writes `secret_key: "__SECRET_KEY__"` into the node's `settings.yml` and
substitutes it with the generated key:

```bash
sed -i '' "s|__SECRET_KEY__|${SECRET_KEY}|" "${INSTALL_DIR}/searxng/settings.yml"
```

Every other mutation in the file carries a `|| fail`; this one carried nothing, and the script runs
under `set -uo pipefail` (no `-e`). If the substitution failed, the container started with the
literal, tracked, publicly known placeholder as its signing key — the outcome the comment above
it promises cannot happen — and the canary still answered JSON, so the run reported READY.

## Fails-before evidence

The pre-fix line, from HEAD, with a `sed` that succeeds but changes nothing on `PATH`:

```
$ git show HEAD:deploy/provision-node.sh | grep -n 'sed -i .*__SECRET_KEY__'
252:sed -i '' "s|__SECRET_KEY__|${SECRET_KEY}|" "${INSTALL_DIR}/searxng/settings.yml"

$ ( PATH=<no-op sed>:$PATH sed -i '' "s|__SECRET_KEY__|abc123def456|" before.yml ); echo exit=$?
exit=0 (0 = the script would have carried on)
and the placeholder is still the signing key: 1 occurrence(s)
```

## The fix

The substitution and two assertions are now a function — the script's own helpers are already
functions, and this one has to be exercisable without provisioning a node:

```bash
install_secret_key() {
    local settings_file="$1"
    local key="$2"
    sed -i '' "s|__SECRET_KEY__|${key}|" "${settings_file}" \
        || fail "could not install the SearXNG secret key into ${settings_file}"
    if grep -qF '__SECRET_KEY__' "${settings_file}"; then
        fail "… still contains the __SECRET_KEY__ placeholder; refusing to start a container that would sign with a known key"
    fi
    if ! grep -qF "secret_key: \"${key}\"" "${settings_file}"; then
        fail "… does not contain the generated secret key; refusing to start"
    fi
}
```

The second check catches a substitution that silently did nothing; the third catches a file that is
missing, empty, or signed with something else. Both use `grep -qF`, so the key is treated as a
literal and never printed.

## Verification — the guard logic exercised with the script's own function

The harness extracts `install_secret_key()` and the settings template **from the script itself**
(no copy of the logic), stubs `fail`, and runs four cases:

```
1. ordinary case: placeholder replaced by the generated key
     exit=0, placeholder gone, key present
2. sed fails (read-only directory)
     exit=3, "could not install the SearXNG secret key into …"
3. sed succeeds but changes nothing (no-op sed on PATH)
     exit=3, "… still contains the __SECRET_KEY__ placeholder …"
4. placeholder gone but the key text is wrong
     exit=3, "… does not contain the generated secret key …"
```

```
$ bash -n deploy/provision-node.sh                       OK
$ shellcheck -S style deploy/provision-node.sh          SC2015 x2, SC2016 x2 — identical to the baseline
```

**Not executed, on purpose:** provisioning itself. Running it would install Docker on a node and
touch the fleet, which the brief forbids. What is verified is the guard: syntax, lint parity, and
the four cases above, driven by the script's own function and template.
