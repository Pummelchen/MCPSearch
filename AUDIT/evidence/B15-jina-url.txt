# B15 — the Jina Reader target was percent-encoded into the path

Host: MacBook-AB.local (arm64, macOS 26.6.2) · branch audit/2026-09-13

## What was wrong

Reader takes the target URL as the *rest of the path*, so it must be appended verbatim.
`baseURL.appendingPathComponent(request.url.absoluteString)` instead percent-encodes the URL's
reserved characters into that path: `?` became `%3F` and `#` became `%23`. The reader was
therefore asked for a different resource — for a search-result or documentation URL with a
query, the common case — and answered 404 or the wrong page.

## Fails-before evidence

```
$ swift test --filter FetchFallbackTests/testTheReaderIsGivenTheTargetURLVerbatim
  # with appendingPathComponent restored:
  XCTAssertTrue failed - the query must reach the reader intact:
    https://reader.invalid/http://127.0.0.1:53870/page%3Fq=swift+concurrency&lang=en%23results
  XCTAssertFalse failed - the query must not be percent-encoded into the path: (same URL)
  XCTAssertFalse failed - nor the fragment: (same URL)
```

Note the shape of the bug: the query *looks* present in the string, but it is part of the path
the reader is given, so the reader fetches a page literally named `page?q=…`.

## The fix

```swift
var readerURL = baseURL.absoluteString
if !readerURL.hasSuffix("/") { readerURL += "/" }
guard let target = URL(string: readerURL + request.url.absoluteString) else {
    throw SearchError.invalidRequest("could not build a reader URL for \(request.url)")
}
```

Appending the strings and parsing the result keeps every reserved character where the target put
it, and the guard keeps a pathological target from crashing the fetch.
