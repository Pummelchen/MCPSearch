# B99 — no test tied the Swift harnesses to the Python harnesses, and two scripts were untested

Host: `node1 (arm64, macOS 26.6.2)` · branch `audit/2026-09-13` · Swift 6.3.3 · Python 3.14

## Premise check: open, but one clause was narrower than written

Measured before writing:

* The scrub list **was** duplicated by hand and **was** unenforced in both directions —
  `ServerTestSupport.providerEnvironmentVariables` (18 entries) and `mcp_smoke.SCRUBBED_VARIABLES`
  (the same 18 today) had no test or CI step linking them.
* `searxng_health.py` (165 lines) had **no test at all**: `grep` found no file referencing `probe`
  or the module except docs, and the only way to run it was against a live instance.
* `soak.py` (539 lines) had **more coverage than the record claims**. `.github/workflows/ci.yml`
  already drives `build_environment`, `silent_providers` and `run_verdict` in two steps (the B23 and
  B44 guards), and `run_verdict` was extracted for exactly that. What was untested was the rest:
  `main`'s argument handling, `parse_dotenv`, `load_secret_values` and `find_credential_leaks`.
* No test drove the two built executables against the same stub endpoint and compared their
  reports. That third clause is a genuine gap, but it is a different contract (server vs monitor
  agreement) from the two the spec leads with, and no stub in the tree currently serves both
  protocols. It is **not** addressed here; see Deviation.

## What was chosen, and why

The spec offers "a test (or CI step) that reads `scripts/mcp_smoke.py` … and asserts set equality"
and, for the scripts, "a CI invocation of `soak.py --queries 1` against a loopback stub (or a
pytest-style test for the script's argument parsing and credential-leak scan) and a unit test for
`searxng_health.probe`'s status classification against a stub HTTP server". This takes the
test-level options in all three cases, in one new module, `scripts/harness_tests.py` (16 tests,
stdlib `unittest`, no new dependency):

| Test | Pins |
| --- | --- |
| `ScrubListContractTests.test_the_python_and_swift_scrub_lists_are_the_same_set` | reads the Swift literal out of `TestSupport.swift` and the tuple out of `mcp_smoke.py`, and fails with the diff in each direction |
| `SearXNGHealthTests` (7) | healthy → exit 0 with `engines`/`engine` both counted; 403 → `json_disabled`/exit 1; 200 with no results → unhealthy/exit 1; non-JSON 200 → `unexpected_response`/exit 1; closed port → `unreachable`/exit 2; `file://` → `invalid_url`/exit 2 (the A08 guard); the human report names a two-element unavailable pair and skips a one-element one |
| `SoakArgumentTests` (7) | `--help` documents every flag; `--queries 0` and `--queries -3` are usage errors (B82); a missing binary reports rather than crashes; `parse_dotenv` handles `export`, both quote styles and a valueless key; `find_credential_leaks` finds markers and long values and ignores short ones; a clean stream reports none; `load_secret_values` reads `SEARCH_CONFIG_FILE` |

The SearXNG cases run against a real loopback `ThreadingHTTPServer` on an ephemeral port, so the
classification is exercised end to end rather than mocked. `.github/workflows/ci.yml` gains one
step in `static-analysis` that runs the module.

**Why not the CI `soak.py --queries 1` invocation.** It needs the release binary and a live SearXNG
stub that speaks the SearXNG JSON API; that stub exists inside `monitor_tty_smoke.py`, not as a
reusable server. Running a real one-query soak would add a build dependency to the fast
static-analysis job and would still exercise none of `soak.py`'s own parsing and leak-scan logic,
which is what the spec's second option names. The existing CI steps already run `run_verdict`
without a soak, for the same reason.

**Why not `tests/python/`.** `ruff` and `pyright` are scoped to `scripts/` (see `ruff.toml` and
`pyrightconfig.json`). A test module under a new top-level `tests/` directory would be the only
Python in the repository outside both gates, which is how the next drift hides. Keeping it in
`scripts/` means the one new file is linted, format-checked and type-checked by the existing steps
with no configuration change, and the CI step is a single `python3 scripts/harness_tests.py`.

## Proof the assertions can fail (mutations)

The scrub-list contract is the one that spans two languages, so it is the one mutated. One entry
was deleted from each list — `"SEARCH_PROVIDER_ORDER", ` from the Swift literal and the
`"DEEPSEEK_MODEL",` line from the Python tuple — so each direction had something to report:

```
AssertionError: Items in the first set but not the second:
'DEEPSEEK_MODEL' : ServerTestSupport.providerEnvironmentVariables names variables
scripts/mcp_smoke.py does not scrub: the smoke test would then pass a developer's exported key
through to the child it believes it scrubbed
Ran 16 tests
FAILED (failures=1)
```

A first attempt miscounted the direction: it deleted only from the Python side, and the failure read
"scripts/mcp_smoke.py scrubs variables the Swift harnesses do not: update
ServerTestSupport.providerEnvironmentVariables in the same commit" — the other message, as
intended. Both files were restored: `diff` empty for each and `shasum -a 256 -c` OK, SHA-256
`068a19ac461be6f7f9ad0cd5b8ef29023d99e39081eddbec36aec3fc867804c8` (`TestSupport.swift`) and
`7b00098f38bc0552bd14219b35bd78dcd7e7843417461b8b71673f60102358c5` (`mcp_smoke.py`).

The SearXNG classification cases fail by construction: each asserts an exact exit code and a JSON
reason, so a change to any arm moves one of them. They were not separately mutated because the
mutation would be a rewrite of the branch under test rather than a one-line break of it.

## Deviation

1. **The test-level option was taken instead of the CI-soak invocation**, for the reasons above.
2. **The "two executables against the same stub" clause is not addressed.** It is a different
   contract from the scrub list, and the SearXNG stub `monitor_tty_smoke.py` uses is not reusable
   as-is; building one that serves both the MCP stdio protocol and the SearXNG JSON API is its own
   task. This artifact records it as still open rather than implying the clause was closed.
3. `soak.py`'s premise was partly stale: its run verdicts and provider selection were already
   driven by CI. Only the parsing, dotenv and leak-scan paths were untested, and those are what the
   new tests cover.
