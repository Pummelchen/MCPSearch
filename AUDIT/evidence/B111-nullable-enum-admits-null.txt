# B111 — nullable enums excluded null, so a strict client could not send the default

Host: this Mac (arm64, macOS 26.6.2, Swift 6.3.3) · branch audit/2026-09-13

## What was wrong

Every optional argument in this file is a nullable union (`["string", "null"]`) and every property
is listed in `required`, which is the documented strict-mode idiom: a client that must fill every
slot sends null to mean "use the default". The runtime parser agrees — `ToolArguments.string`
returns `nil` for `.null` before it looks at the value (`ToolSchemas.swift`, `string(_:)`).

But where such a property also carried an `enum`, the `enum` listed only the choices:

```swift
// ToolSchemas.swift, before
"recency": [
    "type": ["string", "null"],
    "enum": ["any", "day", "week", "month", "year"],
    "description": "Publication time window; default \"any\"",
],
```

In JSON Schema `type` and `enum` are conjunctive: a value must satisfy both. `null` satisfies `type`
and violates `enum`, so the value the design depends on is invalid. Read back from a freshly started
server, the contradiction was visible on the wire for four properties — `web_search.recency` and
`web_search.mode`, and the same two on `web_answer` (`provider` was already fixed in B110):

```
web_search recency type= ['string', 'null'] enum= ['any', 'day', 'week', 'month', 'year']
web_search  mode   type= ['string', 'null'] enum= ['fast', 'balanced', 'thorough']
web_answer recency type= ['string', 'null'] enum= ['any', 'day', 'week', 'month', 'year']
web_answer  mode   type= ['string', 'null'] enum= ['fast', 'balanced', 'thorough']
```

The repository's own lint could not see it: `testToolsAreUsableWithNoOptionalArguments` asserted that
a required-but-nullable property contains `"null"` in its **`type`**, and never looked at `enum`.

## Why `enum` gained null rather than the property losing `required`

The finding offers two repairs. Dropping these properties from `required` would abandon the file's
one optionality idiom — every other argument, in every schema, is a nullable union listed in
`required`; `required` alone is what OpenAI strict mode demands, and the lint enforces
`properties == required` for every object. It would also change the contract for clients that
already fill the slots, and it would make a required-with-null property (`provider`, whose handler
treats `"auto"` and null identically) inconsistent with them. Adding `null` to each `enum` keeps the
idiom and makes the advertised value legal, which is what the parser already implements. That is the
choice made here.

The change is four literals, using the `Value.null` case so the mixed array still types as `[Value]`
(the file's plain `null` spelling is only available where the literal is inferred as `[Value]`
directly, as in `["string", "null"]`):

```swift
// ToolSchemas.swift, after
"recency": [
    "type": ["string", "null"],
    // `enum` and `type` are conjunctive in JSON Schema, so a null the
    // union advertises must appear here too: this property is required,
    // and null is how a strict client asks for the default (ledger B111).
    "enum": ["any", "day", "week", "month", "year", Value.null],
    "description": "Publication time window; default \"any\"",
],
```

The file header's bullet on nullable types now states the pairing rule, and `provider` already
carried null from B110's derived definition. On the wire all six nullable enums now admit null and
the two tools remain identical.

## The lint: nullability is checked against `enum`, not only against `type`

The recursive `violations` walk that already enforces every structural rule now also enforces this
one for every object schema it visits, at any depth:

```swift
// SchemaCompatibilityTests.swift, after (abridged)
if let properties = object["properties"] as? [String: Any] {
    for key in properties.keys.sorted() {
        guard let property = properties[key] as? [String: Any],
            let types = property["type"] as? [String], types.contains("null"),
            let values = property["enum"] as? [Any]
        else { continue }
        if !values.contains(where: { $0 is NSNull }) {
            found.append("\(path).\(key): `type` admits null but `enum` does not, …")
        }
    }
}
```

It is deliberately unconditional on `required`, matching the finding's wording ("for every property
whose `type` includes `"null"`"): a nested nullable enum in an output schema would have exactly the
same contradiction, and property-level nullability is the contract being checked. The rule table at
the top of the test file gained the matching row, and
`testToolsAreUsableWithNoOptionalArguments` — the check that was blind to this — now asserts the
`enum` admits null alongside the `type` assertion it already made.

`testOptionalSearchArgumentsAdmitNull` was added as the focused test. It walks both search tools'
input schemas and requires, for each of `recency`, `provider` and `mode`, that the type is nullable
and the enum contains null, so the failure names the argument a caller cannot express rather than
just the schema object. (`provider` already satisfied it from B110; it is asserted here because the
mirroring means the three belong to one contract.)

## Noted, not changed

The four enums are still literals rather than derived from `Recency` and `SearchMode`; only
`provider` is derived, because B110's finding was about a *drift between two tools* and these are one
literal each. A future `enum`-carrying nullable property is covered by the recursive rule without
further work. The finding's own compatibility caveat stands: no vendor client is run here, so the
client-visible impact is reasoned from the JSON Schema specification and from this server's parser,
not observed against a vendor.
