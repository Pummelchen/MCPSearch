# B101 — `HTTPMCPHost`'s startup-failure and internal-error paths were untested

Host: `node1 (arm64, macOS 26.6.2)` · branch `audit/2026-09-13` · Swift 6.3.3

## Premise check: two of three gaps open, one already closed, one unreachable

`HTTPTransportTests` (835 lines, 13 tests) covers the negative HTTP set well. Checking each of the
record's claims against the tree:

* **`HTTPHostError.bindFailed` — open.** No test started the server on an occupied port, so nothing
  reached `start()`'s `catch` or asserted the error's `description`. `git log --all --grep
  "audit(B101)"` is empty.
* **`describe`/origin acceptance for `localhost` / `::1` / `127.x` — already closed, at the unit
  level.** `LoopbackOriginTests.testLoopbackLiteralsAndLocalhostAreAccepted` covers
  `http://127.0.0.1:8080`, `http://127.255.255.254:1`, `http://localhost:8080`, `http://LOCALHOST`
  and `http://[::1]:8080`. What was *not* covered is the same acceptance **through the server**: the
  cross-origin test asserted a foreign origin, a `127.`-prefixed lookalike and `127.0.0.1` only, so
  `localhost` and `[::1]` had never been served by the HTTP path. That is the sliver worth adding.
* **The `.failure` → 500 "Internal error" arm (`:211-225`, now `:481-489`) — unreachable, not merely
  untested.** It fires only when `dispatch` *throws*. `HTTPMCPHost.handle` returns `MCP.HTTPResponse`
  and never throws, and the SDK transport converts validation rejections into `.error` responses —
  which `createSession` handles separately. Measured directly against the built server (table
  below): every malformed-initialize variant answers 4xx, and the process logs no unexpected error.
  The arm is a defensive catch-all for an error the current SDK cannot produce.
* **The non-loopback startup warning (`:291-297`) — deliberately left untested.** Reaching it means
  binding a real non-loopback interface, which on a CI runner means exposing an unauthenticated
  server on the network. That is not a risk a test should take, so it stays uncovered and is
  recorded here rather than faked.

Measured behaviour of the initialize variants (each against a freshly started server):

```
normal           200
wrong protocol   200   (the SDK negotiates rather than rejecting)
no Accept        406
wrong Content-Type 406
session header   406
non-JSON body    400   (host's own isInitializeRequest guard)
```

## What was added

A new `Tests/WebSearchCoreTests/HTTPMCPHostLifecycleTests.swift` with two tests, plus one minimal
test-visible change: `RawHTTP` and `HTTPTransportTests.freeLoopbackPort` were made internal (from
file-private) so the new file drives the same raw client rather than growing a second ~300-line
socket client. No production code changed.

| Test | Pins |
| --- | --- |
| `testStartingOnAPortAlreadyInUseExitsWithTheBindError` | with the port held by the test, the child exits 1 and stderr carries `Could not bind 127.0.0.1:<port>` and `Address already in use` — i.e. `bindFailed`'s documented `description`, through the only surface the executable exposes for it |
| `testLocalhostAndIPv6LoopbackOriginsAreServed` | `http://localhost:<port>` and `http://[::1]:<port>` are both served 200 on an initialized session, with `http://localhost.attacker.example:<port>` as a 403 control |

`bindFailed`'s `description` is asserted through stderr rather than in-process because
`HTTPHostError` is in the executable target the test target cannot import; the subprocess surface is
the same one `main` prints for an operator, and the expected string is stated in the artifact and
the test comment so a rename is a deliberate decision.

## Deviation

1. The record's "a unit-level assertion of `HTTPHostError.bindFailed(...).description`" is not
   possible in this target (the executable cannot be imported), so the `description` is asserted
   through the startup log the child emits — the same string — rather than by importing the type.
   Exporting the type for a test would be a production change this task does not justify.
2. The `.failure` → 500 arm is **not** covered, because it is unreachable from the HTTP surface: no
   client input makes `dispatch` throw. The initialize-variant table above is the evidence, and the
   test file records the finding.
3. The non-loopback startup warning is left uncovered on purpose: exercising it would put an
   unauthenticated listener on a real interface.
4. The origin arms for `localhost`/`::1` were already unit-tested; only their server-path coverage
   was added, so the record's "origin tests for …" is satisfied at the HTTP layer, not duplicated.
