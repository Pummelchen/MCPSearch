# B113 — configuration was loaded before the command line was parsed

Host: this Mac (arm64, macOS 26.6.2, Swift 6.3.3) · branch audit/2026-09-13

## What was wrong

`main.swift` built the whole configuration — and, below it, the HTTP client and the provider
pipeline — before it looked at `argv`:

```swift
// main.swift, before
let configuration = AppConfiguration.load()
…
let http = URLSessionHTTPClient(configuration: configuration, log: log)
let pipeline = SearchPipelineFactory.make(configuration: configuration, http: http, log: log)
let handlers = ToolHandlers(pipeline: pipeline, log: log)

// Parse command-line options before building the server: a bad flag should fail fast
// and loudly rather than starting the wrong transport.
let options: ServerOptions
do {
    options = try ServerOptions.parse(Array(CommandLine.arguments.dropFirst()))
} catch { … }
if options.wantsHelp { print(ServerOptions.usage); exit(0) }
```

Two consequences, both process-visible:

* The B09 validation arm for `SEARCH_CONFIG_FILE` is fatal *before* `--help` is handled: a
  mistyped config path made `SwiftWebSearchMCP --help` write "Refusing to start" and `exit(2)`
  without printing usage at all. Help depended on the environment.
* Every invocation — including `--help` and one about to be rejected for an unknown flag — logged
  `Starting SwiftWebSearchMCP`, resolved the provider inventory, and constructed the HTTP client
  and the provider pipeline before the flag could be reported. The comment at the old parse site
  ("a bad flag should fail fast and loudly") described an intent the ordering defeated.

## The fix

The parse block moved to the top of the file, above `AppConfiguration.load()`. `--help` is
answered and a bad flag is reported before any configuration is read:

```swift
// main.swift, after
// The command line is parsed before any configuration is loaded. The reverse order meant that a
// mistyped `SEARCH_CONFIG_FILE` refused to start even for `--help`, and a flag that was about to
// be rejected still emitted the startup log and built the HTTP client and the whole provider
// pipeline first (ledger B113).
let options: ServerOptions
do {
    options = try ServerOptions.parse(Array(CommandLine.arguments.dropFirst()))
} catch {
    // The logger takes its level from the configuration, which is deliberately not loaded yet, so
    // this diagnostic goes to stderr directly.
    FileHandle.standardError.write(
        Data(("Invalid arguments: \(error)\n" + ServerOptions.usage + "\n").utf8)
    )
    exit(2)
}

if options.wantsHelp {
    print(ServerOptions.usage)
    exit(0)
}

let configuration = AppConfiguration.load()
```

The parse error no longer goes through `log.error` — the logger's level comes from the
configuration, which by design is not loaded yet — so it is written to stderr directly, followed by
the usage text exactly as before. Nothing else depended on the early `AppConfiguration.load()`: the
issue report, the `unreadableConfigFile` fatal arm, the `Starting` log, the provider inventory and
the empty-configuration warning all sit below the new parse block and still run for a real
invocation. `ServerOptions.usage`, `ServerOptions.parse` and `AppConfiguration.load` are
unchanged; no public signature moved.

## Tests

Three process-level tests were added to `Tests/WebSearchCoreTests/StdioServerTests.swift`, which
already owns the end-to-end harness. A new `runToCompletion(arguments:environment:)` helper starts
the built executable with the same hermetic (credential-scrubbed) environment as the MCP harness,
waits for exit, and returns `(status, stdout, stderr)`.

* `testHelpSucceedsEvenWhenTheConfigurationFileIsUnreadable` — `--help` with
  `SEARCH_CONFIG_FILE=/nonexistent/audit-missing-config.env` exits 0, prints usage on stdout, and
  never writes "Refusing to start".
* `testInvalidFlagIsReportedBeforeConfigurationIsValidated` — `--not-a-flag` under the same fatal
  configuration exits 2 and reports `Unknown argument: --not-a-flag` rather than the config error.
* `testHelpDoesNotLoadConfiguration` — a plain `--help` writes no `Starting` diagnostic, so
  configuration was not loaded at all.

## Noted, not changed

* The `usage` text is still the hand-maintained string B114 owns; this task deliberately reorders
  startup rather than touching it. A `--help` with a *valid* environment still prints the same text
  as before, byte for byte.
* `AppConfiguration.parse`'s empty-value handling (B113's `evidence_before` also mentions the
  unreachable `PARALLEL_MCP_URL=` arm) was left alone: it is B59's recorded behaviour and not part
  of this task's expected-correct, which is only about parse order.
