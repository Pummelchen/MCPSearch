# B121 — `HTTPError.invalidURL`'s detail was echoed into the caller-facing message

Host: `node1 (arm64, macOS 26.6.2)` · branch `audit/2026-09-13` · Swift 6.3.3

## Premise check: confirmed, and still dormant

The interpolation was real and is still there before the fix: `HTTPStatusMapper.map` forwarded
`HTTPError.invalidURL`'s free-form `detail` straight into
`SearchError.unsupportedRequest(provider, detail)`, which renders as
`"<Provider> cannot serve this request: <detail>"` — both in `SearchError.safeDescription` and in
`ToolHandlers.errorMessage(for:)`, which uses the same wording. A URL-shaped detail therefore reached
the client with any credential in its query string.

`git grep` at this revision finds **no production call site that throws `invalidURL`**. The only
occurrences in `Sources/` are the declaration (`HTTPClient.swift`), its `isTransient` arm, and the
mapper itself; the `invalidURL` in `AppConfiguration`/`main.swift` is a different enum
(`ConfigurationIssue.invalidURL`). So the case is dormant and the grading stays **S3** — no
production thrower has appeared since the finding was written, and the severity does not change.

## The fix

`Sources/WebSearchCore/Providers/HTTPStatusMapper.swift`, the mapper's `HTTPError` switch:

```diff
-            case .invalidURL(let detail):
-                return .unsupportedRequest(provider, detail)
+            case .invalidURL:
+                // The detail is free-form and may be URL-shaped, so it must never reach the
+                // caller: a key that travels in a query string would be echoed in full. Like
+                // the `URLError` arm below, the message is curated from the case rather than
+                // interpolated from whatever the transport happened to write (ledger B121).
+                return .unsupportedRequest(provider, "the request URL could not be built")
```

This is the audit's existing mechanism rather than a second one: the same arm already curates a
`URLError` from its code with `HTTPError.reason(for:)` (commit `0edc66b`, A07), so nothing from a
platform-supplied or free-form string reaches a diagnostic. The construction site now passes a fixed,
code-derived phrase; `invalidURL`'s associated value is still carried on the error for an operator
reading `String(describing:)`, but it can no longer be forwarded to a caller. No public API signature
changed — `HTTPError.invalidURL(String)` keeps its payload.

## The test

`Tests/WebSearchCoreTests/HTTPStatusMapperTests.swift`:

* `testMapClassifiesEveryHTTPErrorCase`'s `invalidURL` row now feeds a credential-bearing URL
  (`https://api.mojeek.com/search?api_key=tvly-not-real`) and expects the curated
  `unsupportedRequest(.tavily, "the request URL could not be built")`, so the table proves the detail
  is discarded instead of coincidentally matching.
* `testMappedDescriptionsNeverEchoARequestURL` gained a `HTTPError.invalidURL(secretURL)` row, so the
  URL, the key and the host are all asserted absent from the rendered description. Its doc comment no
  longer records the hazard as uncovered.

Together with `testMapClassifiesEveryHTTPErrorCase` the two assertions form the requested test: an
`invalidURL` carrying a credential is mapped, and the secret is absent from what the caller sees.

.unsupportedRequest(provider, detail)`), the source was touched so the same-second staleness could not
hide the edit, and the test bundle was rebuilt before the run. Verbatim:
