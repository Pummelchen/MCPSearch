B122 — a caller's cancellation during answer synthesis is propagated, not reported as a failure
================================================================================================

Task    : B122 (S3, category bug) — sources: AUDIT/ledger.json, AUDIT/ledger.md
Branch  : audit/2026-09-13
Host    : node1 (Mac14,3, arm64, macOS 27.0, Xcode 27.0, Swift 6.4, 8 GB)

The defect
----------
`AnswerSynthesizer.complete` folded every transport error into
`SearchError.synthesisFailed(Self.describe(error))`. A caller's cancellation reaches it in one of
two shapes, because `URLSessionHTTPClient` reports them differently:

  * `CancellationError` — thrown by `URLSessionHTTPClient.send`'s pre-flight
    `try Task.checkCancellation()` (the task was already cancelled when the request was built); or
  * `HTTPError.cancelled(label:)` — produced when the request was in flight, from either
    `perform`'s `catch is CancellationError` or its `URLError.cancelled` mapping.

Neither shape could reach `ToolHandlers.webAnswer`, whose `catch is CancellationError` arm for the
synthesis phase was therefore unreachable. A cancelled `web_answer` returned **success**, carrying
the search results and a warning. This is the same class `B04` fixed for the search and fetch paths,
and `B97` had pinned the mapping as intended behaviour — so the ledger recorded B122 as BLOCKED on a
contract decision rather than a mechanical fix.

Decision (and the alternatives rejected)
----------------------------------------
Resolved as **propagate cancellation**, the posture `B04` established for the other two paths.

  1. *Delete the tool layer's arm as dead code.* Rejected. It is smaller, but it would leave the
     synthesis path as the only one of three that reports a caller's cancellation as a failure, and
     it removes the symptom while keeping the inconsistency.
  2. *Leave B122 BLOCKED for the maintainer.* Rejected for this session: the brief requires the
     technically correct solution to be chosen, with the rejected alternatives documented.

Because the winning option contradicts a pinned expectation, the check was corrected in the same
commit as its own recorded change (see "Re-pinning B97" below) rather than weakened.

The change
----------
`Sources/WebSearchCore/Search/AnswerSynthesizer.swift`

  * `complete` rethrows both cancellation shapes as `CancellationError`, before the generic
    `synthesisFailed` arm.
  * `synthesize` adds `try Task.checkCancellation()` after the answer arrives, closing the race in
    which the response lands after the caller has gone — the same boundary
    `SearchOrchestrator.search` draws after its fan-out and `WebFetcher.open` draws before its
    reader fallback.
  * `describe`'s two cancellation arms are deliberately retained: they remain the curated mapping
    for a cancellation that is *not* the calling task's, and `describe` is a pure helper whose arms
    are unit-tested directly — the same is already true of its `URLError` arms, which
    `URLSessionHTTPClient` maps to `HTTPError` before they can reach it.

Re-pinning B97
--------------
`AnswerSynthesizerTests.testCancellationDuringSynthesisIsReportedAsCancelled` asserted that a
cancellation surfaced as a `SearchError` whose description contained "cancelled". That was accurate
about the code and wrong about the contract; it is replaced by
`testCancellationDuringSynthesisPropagatesAsCancellation`, which asserts the exact error type and
rejects any other — strictly stronger than the version it replaces, which accepted any `SearchError`
mentioning cancellation. A second test,
`testInFlightCancellationReportedAsHTTPErrorAlsoPropagates`, pins the `HTTPError.cancelled` shape.
