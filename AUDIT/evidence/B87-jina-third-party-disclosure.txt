# B87 — the Jina Reader fallback hid the third-party disclosure

Host: this Mac (arm64, macOS 26.6.2, Swift 6.3.3) · branch audit/2026-09-13

## What was wrong

`enableJinaReaderFallback` defaults to `true`, so by default every `web_open` whose native
extraction is thin sends the **full target URL** to `r.jina.ai`, which fetches the page on this
server's behalf. `web_open` accepts authorisation-bearing URLs, so that URL can carry a token,
a signed query parameter or an internal-looking path that the model chose. Nothing told the caller:

* the model-visible tool description said only "JS-heavy pages may fall back to a rendering
  service" — it did not say the URL left the machine or name the service;
* the README said nothing about the reader at all;
* the result warning on the fallback path said only "used Jina Reader instead", without naming
  the disclosing third party. Worse, when the native fetch failed outright and the reader succeeded,
  **no warning was emitted at all**, because the warning was only appended inside `if let directResult`.

The behaviour itself is an accepted, documented, toggleable design decision and the SSRF policy
still gates what can be fetched, so this is a disclosure gap, not a control failure.

## The fix: disclose the fact in every channel, do not weaken or disable anything

There was no false *code* claim to reconcile — the code did what it does — so this is the
"omit a disclosure the operator needs" half of the task. The fix states the fact where each
audience looks, rather than softening anything:

1. **Tool description** (`MCPServer.swift`): now names Jina Reader and `r.jina.ai` and says the
   URL is fetched remotely, so the model sees the disclosure before it calls the tool.
2. **README** (`## Tools` → new `### Third-party rendering for web_open`): states that the full
   URL, including credentials/tokens/signed query parameters, goes to the third party; names the
   two env vars (`SEARCH_ENABLE_JINA_READER=false` to disable, `JINA_API_KEY` for the rate limit);
   and records that the SSRF policy runs first.
3. **Result warning** (`JinaReaderFetcher.fetch`): every successful reader result now carries
   `"Used Jina Reader (<host>), a third-party service that fetched this URL remotely."` The host
   is derived from the configured `baseURL`, so a non-default reader endpoint is named correctly
   and the message is not hardcoded to `r.jina.ai`. Putting it in the reader (rather than in
   `WebFetcher`'s thin-native branch) closes the direct-failure gap: the disclosure now travels
   with any reader result, on every path.

The fallback stays enabled by default, the URL policy is untouched, and no public signature
changed. **Redaction was considered and deliberately not done**: the finding marks it a
"consider", userinfo/query redaction changes which resource the reader fetches (a query is often
load-bearing), and gating it needs a new operator opt-in, which is a behaviour change belonging to
an operator decision rather than this disclosure task. It is recorded as left open rather than
silently omitted.

## The tests, and proof they can fail

Two tests pin the disclosure, one per channel, plus a strengthened assertion:

* `StdioServerTests.testWebOpenDescriptionDisclosesTheThirdPartyReader` starts a real server,
  reads `tools/list` as a client would, and requires the `web_open` description to contain
  `r.jina.ai`, `third-party` and `remotely`. This is the assertion that would have caught the
  omitted disclosure in the model-visible text.
* `FetchFallbackTests.testAReaderSuccessAfterADirectFailureStillDisclosesTheThirdParty` covers the
  path that previously emitted no warning at all (direct fetch fails, reader succeeds).
* `FetchFallbackTests.testThinNativeExtractionFallsBackToTheReader` was strengthened to require the
  disclosure on the ordinary fallback result.

## Noted, not changed

* Query/userinfo redaction on the fallback path is left open on purpose (see above).
* The README does not enumerate `SEARCH_ENABLE_JINA_READER` in a configuration table; the new
  section names it inline, which is where a `web_open` operator will read it. The wiki
  Configuration page remains the exhaustive list.
* `JinaReaderFetcher` is constructed only by `SearchPipelineFactory`; the warning is emitted by the
  fetcher itself, so a future direct caller cannot bypass the disclosure.
