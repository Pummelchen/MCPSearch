# B96 — the status mapper's `HTTPError` arms and `validate`'s default/422 paths were untested

Host: `node1 (arm64, macOS 26.6.2)` · branch `audit/2026-09-13` · Swift 6.3.3

## Premise check: still open, and B17/B57 had not moved it

Grepped before writing. `HTTPStatusMapper.map` was called by exactly one test
(`ErrorReportingTests.testTransportErrorTextNeverEchoesTheRequestURL`, with a `URLError`), so every
`HTTPError` arm was unverified; `validate` was exercised only by
`ProviderContractTests.testHTTPStatusMapperClassifiesCorrectly`, which covered
401/403/429/400/503/200 — no 422, no unmapped status. B17 (secret-key guard) and the recent provider
work did not add coverage here; the mapper file itself is unchanged since it was written.

## Two measurements that changed the assertions

Running the new table found two places where my first draft asserted something the code does not do:

* `.cannotConnectToHost` is curated as `"could not connect to the host"`, not `"the host could not be
  resolved"` (that is `.cannotFindHost`/`.dnsLookupFailed`). The assertion now says what the code
  says.
* `validate` treats 204 as a success, because `HTTPResponse.isSuccess` is `(200..<300)`. The first
  draft asserted it took the default arm; it now sits in the success-range test.

## A finding this test surfaced, not asserted away

`HTTPError.invalidURL(detail)` is interpolated verbatim by `map` into
`SearchError.unsupportedRequest(provider, detail)`, whose `safeDescription` renders as
`"Mojeek cannot serve this request: \(detail)"`. A URL-shaped detail is therefore echoed:

```
HTTPError.invalidURL("https://api.mojeek.com/search?api_key=tvly-not-real")
  -> Mojeek cannot serve this request: https://api.mojeek.com/search?api_key=tvly-not-real
```

`git grep` finds **no production call site that throws `invalidURL`** — the case exists for the
transport adapters and is currently dormant — so this is not an active leak. The first draft of
`testMappedDescriptionsNeverEchoARequestURL` asserted it was safe; that was wrong, and rather than
delete the finding, the test now covers the three descriptions the transports actually produce and
the file's doc comment records the hazard. It belongs to whichever task owns `HTTPError`'s
construction, not to a test-only item.

## Deviation

The expected-correct asks that a `safeDescription` carry no request URL, and this test found one
case where a URL-shaped `invalidURL` detail would be echoed. The case has no production thrower, so
there is no behaviour to fix under a test-only task; the limitation is asserted around and recorded
here and in the test file rather than silently dropped or "fixed" by weakening the string.
