# B74 — `--no-nodes` was silently ignored when a `--node` was also present

Host: this Mac (arm64, macOS 26.6.2) · branch audit/2026-09-13

## What was wrong

`--no-nodes` set an empty node list inside the parse loop, and the custom `--node` list was applied
unconditionally *after* the loop:

```swift
if !customNodes.isEmpty { options.nodes = customNodes }
```

So `mcps-mon --node n1=… --no-nodes` still probed `n1` — the "do not probe" flag lost to the flag
that names a node, in either order, while `--no-nodes` alone worked. The usage text presents the
flags as order-independent; the code made the outcome depend on which one the loop saw last.

## Fails-before evidence

```
$ swift test --filter testNoNodesOverridesACustomNodeListInEitherOrder
error: ... ["--node", "stub=...", "--no-nodes"] must probe nothing, got ["stub"]
error: ... ["--no-nodes", "--node", "stub=..."] must probe nothing, got ["stub"]
```

## The fix

A `nodesDisabled` flag records the request, and it wins after the loop; a `--node` list the operator
also passed is reported rather than silently dropped:

```swift
if nodesDisabled {
    if !customNodes.isEmpty {
        options.notes.append("--no-nodes overrides the --node list; no node is probed")
    }
    options.nodes = []
} else if !customNodes.isEmpty {
    options.nodes = customNodes
}
```
