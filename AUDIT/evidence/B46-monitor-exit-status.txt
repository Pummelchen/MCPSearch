# B46 — `mcps-mon` always exited 0, so `--iterations` was not a health check

Host: this Mac (arm64, macOS 26.6.2, Swift 6.3.3) · branch audit/2026-09-13

## The premise, checked first

True as reported, and no prior fix existed:

```
$ grep -rn "exit(" Sources/MCPSMonitor/ ; git log --oneline --all --grep "audit(B46)"
Sources/MCPSMonitor/main.swift:501:    exit(0)          # --help
Sources/MCPSMonitor/main.swift:505:    exit(2)          # parse error
                                              # no B46 commit anywhere on the branch
```

The refresh loop ended at the bottom of `main.swift` with no `exit` call at all, so a scripted
run returned the C runtime's default status 0 whatever the probes found. The sibling operator
tool documents a real status contract — `scripts/searxng_health.py`: "Exit codes: 0 healthy,
1 the instance or its JSON API is unusable, 2 unreachable" — which is the precedent followed
here. `SignalRestore` deliberately `_exit(0)`s on an external SIGINT/SIGTERM ("a supervisor
asking us to stop is a clean shutdown"), and that is left unchanged.

## The contract chosen

Defaults, documented in `Options.usage` under a new `EXIT STATUS` section:

* **0** — the fleet answered: at least one probed node returned results, and, when any
  provider was configured, at least one of them was healthy. A run that checked nothing
  (no nodes, no configured providers, or no completed refresh) also reports 0.
* **1** — every probed node failed to return results, or every configured provider failed.
  A `degraded` node — answered but returned nothing usable — counts as failed.
* **2** — invalid arguments. Unchanged; parsing already did this before any probe.

`--exit-zero` forces 0 for a purely graphical run. This is a deliberate behaviour change and
is called out as one: anyone who today pipes `mcps-mon > frame.txt` or runs
`mcps-mon --iterations n` will now get 1 when the whole fleet is down. That is the point of
the finding — the status could not previously distinguish the two — and the flag is the
opt-out the finding asks for. It does not change the interactive exit path when the fleet is
healthy, and the PTY smoke test's stub is healthy, so its `q`/SIGINT/SIGTERM exit-0
assertions still hold (measured below).

## The test added

Ten cases in `Tests/MCPSMonitorTests/MonitorOptionsTests.swift` under `// MARK: - Exit status
(ledger B46)`: a healthy fleet is 0, all nodes down is 1, all-degraded is 1, one node up is 0,
all configured providers failing is 1, all `NO KEY` is 0 (an unconfigured provider is not a
failure), a run that probed nothing is 0, no model is 0, `--exit-zero` turns a dead fleet's 1
into 0, and the usage text documents the flag and the section.

## The contract measured on the real process

The unit test pins the decision; this shows the process actually returns it. No provider key
in the environment, so no provider can be configured and only the node term can fire. The
dead node is a closed loopback port (connection refused, no external network):

```
$ BIN="$SCRATCH/arm64-apple-macosx/debug/mcps-mon"
$ env -i PATH="$PATH" "$BIN" --iterations 1 --node dead=http://127.0.0.1:9 >/dev/null 2>&1; echo $?
1
$ env -i PATH="$PATH" "$BIN" --iterations 1 --node dead=http://127.0.0.1:9 --exit-zero >/dev/null 2>&1; echo $?
0
$ env -i PATH="$PATH" "$BIN" --iterations 1 --no-nodes >/dev/null 2>&1; echo $?
0
```

## Noted, not changed

* The signal path still `_exit(0)`s. A supervisor stopping a *graphical* run is not asking for
  a health verdict, and changing that would make `kill` report a failure for a deliberate
  shutdown. The signal branch is asserted by the smoke test above.
* `exitCode` filters providers with `state != .notConfigured`. B76 introduces a state for an
  operator-disabled provider, which is likewise not a failure; that task owns the expression
  and must extend this filter when it adds the case, or a fully disabled fleet would report 1.
