# B70 — the subprocess harness "timeout" could not fire

Host: `node1 (arm64, macOS 26.6.2)` · branch `audit/2026-09-13` · Swift 6.3.3

## Premise check: still open

The three stdio harnesses each read stdout like this:

```swift
// before — StdioServerTests.swift:107-136 (same shape in the other two)
let deadline = Date().addingTimeInterval(timeout)
while Date() < deadline {
    if let newlineIndex = stdoutBuffer.firstIndex(of: UInt8(ascii: "\n")) { ... return object }
    let chunk = stdoutPipe.fileHandleForReading.availableData   // blocks
    if chunk.isEmpty { throw ...unexpectedEOF(...) }
    stdoutBuffer.append(chunk)
}
throw ServerTestError.timeout
```

`FileHandle.availableData` blocks until data arrives or the pipe reaches EOF, and the child
holds the write end open, so an infinite loop inside the server is an infinite block inside the
harness. The `while Date() < deadline` test can only run *after* a read returns, which is the
one thing a wedged server never lets happen. The 15 s (`StdioServerTests`, `readMessage`) and
20 s (`ErrorReportingTests`, `SchemaCompatibilityTests`) bounds were therefore decoration.

Confirmed live rather than by reading: with the pre-fix loop in place, the new regression test
below hangs (see the mutation section) instead of failing after its 0.3 s budget.

## The fix

One change, in the shared harness the other two copies are being folded into (B71): every read
now waits in `poll(2)` on the stdout descriptor with the time that is actually left, so expiry
is enforced while the child is alive and silent.

```swift
// TestSupport.swift — ServerProcess.readMessage
// Rounded up so a sub-millisecond remainder still polls once rather than
// expiring early; a negative remainder is discarded by `guard`.
let remaining = Int32((deadline.timeIntervalSinceNow * 1_000).rounded(.up))
guard remaining > 0 else { throw ServerTestError.timeout }

var descriptor = pollfd(fd: stdoutPipe.fileHandleForReading.fileDescriptor, events: Int16(POLLIN), revents: 0)
let ready = poll(&descriptor, 1, remaining)
if ready == 0 { throw ServerTestError.timeout }
if ready < 0 {
    if errno == EINTR { continue }   // a signal must not reset the bound
    throw ServerTestError.timeout
}

let chunk = stdoutPipe.fileHandleForReading.availableData
if chunk.isEmpty { throw ServerTestError.unexpectedEOF(stderr: stderrText()) }
stdoutBuffer.append(chunk)
```

Two details that a naive `poll` conversion gets wrong:

* A complete line already buffered is served **before** the deadline is consulted, so an
  answer that arrived on the previous read is never discarded as a timeout.
* `poll` is restarted on `EINTR` with the recomputed remainder, so an unrelated signal does
  not silently extend the wait.

`readResponse(id:timeout:)` likewise carries one deadline across the notifications it skips,
instead of passing `max(0.1, …)` into a helper that could then block for that floor.

The harness now also owns a shared stderr buffer: `stderrText()` accumulates what it drains, so
the two `StdioServerTests` assertions that used to read `stderrPipe` directly cannot consume a
diagnostic before the assertion that needs it (and the pipe stays private to the harness).

## The test

`StdioServerTests.testHarnessDeadlinePreemptsABlockedRead` runs a child that writes a partial
line and then holds the pipe open, and requires the read to throw the harness timeout rather
than block:

```swift
let server = ServerProcess(
    binary: URL(fileURLWithPath: "/bin/sh"),
    arguments: ["-c", "printf 'partial line with no newline'; sleep 60"]
)
try server.start()
defer { server.stop() }

let started = Date()
XCTAssertThrowsError(try server.readResponse(id: 1, timeout: 0.3)) { error in
    XCTAssertEqual(String(describing: error), "timed out waiting for a response", ...)
}
XCTAssertLessThan(Date().timeIntervalSince(started), 10, ...)
```

`/bin/sh` stands in for the server because the defect is in the read loop, not the binary; the
`printf` with no newline is what makes it a *blocking* read (the loop has data in its buffer
but no complete line, so a poll-less implementation parks in `availableData`).
