# B92 — `web_open`'s Jina path hard-set `final_url` to the requested URL

Host: node1 (arm64, macOS 26.6.2, Swift 6.3.3) · branch audit/2026-09-13

## What was wrong

`JinaReaderFetcher.fetch` decoded the reader's JSON envelope but read only `data.content` and
`data.title`; `finalURL` was hard-set to the requested URL:

```swift
// JinaReaderFetcher.swift, before
return FetchResult(
    finalURL: request.url,
    ...
```

and the unused fields were decoded anyway:

```swift
struct ReaderResponse: Decodable {
    let code: Int?
    let status: String?
    let data: Data?
    struct Data: Decodable { let title: String?; let url: String?; let content: String? }
}
```

So `ToolOutputFormatter.openStructured` reported `final_url` equal to the requested URL even when
the reader reported a different one, while the direct-HTTP path reports the URL it actually
reached. The two extraction methods disagreed about what `final_url` means.

## What the reader actually reports (checked, not assumed)

The ledger's note says the JSON field carries "the URL it actually resolved to". Reading the
reader's own source (`jina-ai/reader`, the open-source branch that the README says was
re-synchronised with the SaaS code in 2026-04) shows `src/services/snapshot-formatter.ts` builds
the field as:

```ts
const formatted: FormattedPage = {
    ...
    url: nominalUrl?.toString() || snapshot.href?.trim(),
```

`nominalUrl` is the `targetUrl` the crawler took from the request path
(`src/api/crawler.ts`: `formatSnapshot(crawlerOptions, scrapped, targetUrl, this.urlValidMs)`),
so for `r.jina.ai` the field is the **nominal target**, not the post-redirect URL; `snapshot.href`
(the real loaded URL) is only used when no nominal URL was supplied. No response header exposes the
resolved URL either. So using `data.url` cannot, by itself, make this path report a redirect — the
field is the reader's echo (possibly normalised) of what was asked for.

The change was still made, because the field is third-party input that the code rendered
verbatim and now validates, and because a reader that does report a different URL (the
`snapshot.href` path, a self-hosted reader, or a future reader) is now followed. **This is a
deviation from the finding's stated impact: the fix honours and validates the reported URL, but it
does not deliver redirect transparency for the hosted reader, because that reader does not publish
the resolved URL.** No honest in-process fix can: the only way to observe the redirect would be to
fetch the target ourselves first, duplicating the fetch and the policy hop, which is not warranted.

## The fix

* the JSON envelope's `data.url` is parsed through a new `resolvedURL(_:)` helper and used as
  `finalURL` when it is usable;
* it is used only when it parses to an absolute `http`/`https` URL with a non-empty host — absent,
  relative, `file:`, `javascript:` and `https://` all fall back to `request.url`;
* the now-unused `code`/`status` fields were dropped from `ReaderResponse`, which is the spec's
  "drop the unused fields" option;
* the markdown/text path is unchanged (`reportedURL` is nil there), so it still reports the
  requested URL, and `URLSource` was deliberately not parsed because the reader fills it from the
  same nominal value.

## Tests

Both in `Tests/WebSearchCoreTests/FetchFallbackTests.swift`, in the existing
`// MARK: - JinaReaderFetcher` section:

* `testReaderJSONEnvelopeURLBecomesFinalURL` — a JSON envelope whose `data.url` is
  `https://example.com/resolved` while the request is `https://example.com/page`; asserts
  `finalURL` follows the envelope.
* `testReaderFallsBackToTheRequestedURLWhenTheReportedURLIsUnusable` — table over `nil`, `""`,
  a relative URL, a scheme-relative URL, `file:///etc/hosts`, `javascript:alert(1)` and
  `https://`; asserts each falls back to the requested URL.

## Noted, not changed

The behaviour change for the hosted reader is limited to its own normalisation of the target URL
(for example a trailing slash the caller omitted), which is what the reader says it handled. The
envelope path still uses the reader's HTTP status for failure classification; `code`/`status` were
dropped rather than used, because the reader's envelope `code` is its own status channel and the
existing HTTP-status mapping is the tested one.
