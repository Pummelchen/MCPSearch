## What was wrong (the ledger's `evidence_before`)

When a stale build crashed the monitor at startup, the harness failed with "timed out waiting for
the first frame" — true but misleading: the process had already died and printed "Program crashed:
Signal 11". A crash and a hang were therefore indistinguishable from the failure text.

## Where the fix is (already committed; no diff to review)

`scripts/monitor_tty_smoke.py`, in `run()`, immediately after the startup drain and before any
frame wait (`:396-406`):

```
        # 1. A full-screen display hides the cursor and clears the screen on start.
        #
        # A monitor that dies during startup must be reported as a crash with its exit status, not
        # as a frame that never arrived: that is how B104's stale build was first misread as a
        # timeout (ledger B106).
        session.drain(3.0)
        require(
            session.process.poll() is None,
            "the monitor exited during startup with "
            f"{session.process.poll()}: {ANSI.sub('', session.transcript)[-300:]!r}",
        )
```

## How a crash is distinguished from a hang

`Session` attaches the child's stdin, stdout **and** stderr to the same PTY, so the crash banner
lands in `session.transcript`. After a fixed `drain(3.0)` the check polls the child:

* `poll()` is not `None` → the child is dead, so the failure names **the crash**: the exit status
  and the ANSI-stripped tail of the transcript (the child's stderr). It cannot be an unrelated
  frame condition, because no frame is asserted yet.
* `poll()` is `None` → the startup check passes, and the existing `wait_for(… "the first frame")`
  still times out for a live process that never paints one. That is the hang path, unchanged.

So a dead process fails on the exit code and a live one fails on the frame wait; the two are no
longer the same message.

## Residual, reported but not fixed here

The startup check runs **once**, after the fixed `drain(3.0)`. A monitor that crashes *after* that
window but before its first frame is still reported as a frame timeout. Probe (`late_crash_monitor.py`,
which starts, sleeps 5 s, then writes a crash banner and exits 3):

```
$ python3 - "$HOME/Library/Caches/MCPSearch/B106/late_crash_monitor.py" <<'PY'
… importlib-load scripts/monitor_tty_smoke.py …; m.run(sys.argv[1]) …
PY
failure: timed out waiting for the first frame
exit:0
```

That is a narrower instance of the same shape as B106, but it is outside the fix the ledger's
`expected-correct` states ("a startup check … before any frame wait times out", which is what the
committed code implements), and closing it would mean polling the child inside `wait_for` — a
larger change than this evidence-only completion. It is left for the ledger owner to fold as a new
finding if wanted, and it is called out here rather than silently ignored.

## What is not verified

The real `mcps-mon` binary was not exercised: a concurrent worker owns the Swift build directory,
so `swift build`/`swift test` were forbidden (and no binary is built in this checkout). This does
not weaken the proof, because the defect and the fix live entirely in the Python harness, not in
the binary: the check under test is harness control flow (`Popen.poll()` versus the frame wait),
and the stub reproduces exactly the two states that flow branches on — a child that has exited with
a diagnostic on its stdio, and a child that is alive and silent. The stub's exit status and banner
are read back out of the failure message, so the assertion is on the harness's own output, not on
the stub. What is *not* shown is the real Swift runtime's exit status on a fatal signal; the
harness reports whatever `poll()` returns, so that detail is independent of this fix.
