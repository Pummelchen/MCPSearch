# B66 — decoded-but-unused fields across five vendor DTOs

Host: this Mac (arm64, macOS 26.6.2, Swift 6.3.3) · branch audit/2026-09-13

## What was wrong

Five provider adapters declared `Decodable` fields that no code path reads. They are inert at
runtime — an undecoded or decoded-and-ignored key is the same over the wire — but each one tells a
reader the value is part of the contract and silently absorbs wire drift that should be visible:

| adapter | fields |
| --- | --- |
| Mojeek | `Body.Head.start`, `Body.Head.return`, `Body.Item.date`, `Body.Item.pdate` |
| Exa | `ExaResponse.requestId`, `ExaResponse.resolvedSearchType`, `Item.author`, `Item.summary` |
| SearXNG | `SearXNGResponse.query`, `.corrections`, `.suggestions`, `Item.category` |
| Tavily | `TavilyResponse.query` |
| Brave | `BraveResponse.type`, `BraveErrorResponse.ErrorBody.id/.status/.detail` |

`BraveErrorResponse.type` is a sixth instance the finding did not enumerate: it is read by nothing
either (`validate` reads only `error.code` and `error.meta.component`), so it is removed with the
same rationale. Every field in the list is an `Optional` stored property.

## The decision, and the decoding question

The fields are deleted, not surfaced: the alternatives in the finding (`corrections`/`suggestions`
as warnings) would add a new user-visible behaviour and belong to their own task. This is the same
call `a375ddd`/`e60203e` made for Brave's earlier dead wire surface and `B78` made for the dead
provider states.

**Does removing a decoded-but-unread property change decoding?** Checked field by field, and no:

* Every removed property is `Optional`. Swift's synthesized `init(from:)` decodes an optional
  property with `decodeIfPresent`, so the key was never *required* and no other property's decoding
  depends on it; JSON keys with no matching property are ignored. Deleting an optional stored
  property therefore cannot change how any surviving field decodes. The dangerous shape would be a
  **non-optional** dead field, which would make the key mandatory; none of the fifteen is
  non-optional.
* Two of the DTOs carry an explicit `CodingKeys`: SearXNG's `SearXNGResponse` and Tavily's
  `Item`. In SearXNG the `query`, `corrections` and `suggestions` cases were removed together with
  their properties, and the surviving cases (`results`, `answers`, `unresponsiveEngines`) keep their
  exact spellings — including the `unresponsive_engines` rename — so the mapping is unchanged.
  Tavily's `Item.CodingKeys` was not touched; only the top-level `query`, which had no explicit
  mapping, was removed. `BraveErrorResponse` and `ExaProvider.ExaResponse` use synthesized keys
  throughout.
* Empirically: the fixtures still carry `requestId`, `corrections` and `suggestions`, and the full
  suite is green, so the decoder still tolerates all of them as unread input.

The DTOs are `Decodable` only (no `Encodable` conformance), so nothing is ever encoded from them and
the deletion cannot change any outgoing request or log.

## Noted, not changed

The dead fields' *values* were never surfaced, so the finding's alternative direction (rendering
SearXNG `corrections`/`suggestions`) is left for a task that owns that user-visible behaviour. The
wire contract for what is consumed — `totalEstimatedMatches`, the result fields, the Brave altered-
query warning, the SearXNG unresponsive-engine warnings — is untouched, and the provider contract
tests that drive all five adapters against scripted transports still pass.
