# B85 — the log query digest was a public FNV-1a documented as non-reversible

Host: this Mac (arm64, macOS 26.6.2, Swift 6.3.3) · branch audit/2026-09-13

## What was wrong

`Log.hash` rendered a query as an unkeyed FNV-1a digest and its doc claimed "Stable,
non-reversible short hash for correlating repeated queries without recording user content":

```swift
// Logging.swift, before
/// Stable, non-reversible short hash for correlating repeated queries without
/// recording user content.
public static func hash(_ value: String) -> String {
    var hash: UInt64 = 0xcbf2_9ce4_8422_2325
    for byte in value.utf8 {
        hash ^= UInt64(byte)
        hash = hash &* 0x0000_0100_0000_01b3
    }
    return "q" + String(hash, radix: 16)
}
```

FNV-1a has no key. Hashing is a genuine improvement over verbatim logging, but "non-reversible"
was false: search queries are low-entropy natural language, so anyone holding a log line can hash a
candidate dictionary with the same public function and confirm or recover the query. The offline
check is one line, and 64 bits is no obstacle at that dictionary size. The exposure is real for
whoever reads the logs — a collector, an operator, a pasted bug report.

## The fix: make it resistant, not weaker wording

The finding allowed either renaming this a *correlation id* or making the digest actually
resistant. **The second was chosen**: the underlying fact — a reader can recover the query — is the
problem, and relabelling it would leave that fact in place while removing the only sentence that
warned about it. That is exactly the "softening the wording instead of fixing the fact" the
finding's own structure distinguishes against.

`hash` is now HMAC-SHA-256 under a 256-bit `SymmetricKey` generated once, in memory, at process
start, truncated to the same 64-bit `q` + hex shape, so **no log consumer sees a changed field
format**:

```swift
private static let queryHashKey = SymmetricKey(size: .bits256)

public static func hash(_ value: String) -> String {
    let mac = HMAC<SHA256>.authenticationCode(for: Data(value.utf8), using: queryHashKey)
    var truncated: UInt64 = 0
    for byte in mac.prefix(8) {
        truncated = (truncated << 8) | UInt64(byte)
    }
    return "q" + String(truncated, radix: 16)
}
```

The key is never persisted, never logged and never leaves memory, so a dictionary attack now needs
it. CryptoKit was already a dependency (`SearchCache.swift` uses `SHA256`), so this adds no package.

**The cost, stated in the code.** Because the key is per process, an id is reproducible *within* a
run but not across restarts. That is the price of the in-memory key the finding prescribes, and the
doc now says so instead of promising "stable". The prior FNV value was stable forever, but that
stability is precisely what made it attackable. `Log.hash` is only consumed by
`Log.queryDescription`, which is only used in log metadata, so nothing else depends on cross-run
equality. No public signature changed.

## Proof the test can fail

The new `LoggingTests.testHashIsNotTheUnkeyedFNV1aDigest` pins the *old* defect directly: it holds
the exact FNV-1a outputs the defective function produced for three inputs (computed independently
of the Swift code, with a Python FNV-1a implementation) and asserts the current digest differs. A
revert to FNV-1a fails it.

## Noted

No README or operator-facing doc repeated the non-reversible claim — the false statement was only
in the source doc comment — so there was no second wording to correct. The `q` + hex field and the
`SEARCH_LOG_QUERIES` opt-in are unchanged for existing log consumers.
