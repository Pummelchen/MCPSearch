# B86 — provisioning wrote through fixed, predictable `/tmp` paths, and loaded an image from one

Platform: arm64 macOS · bash 3.2 · shellcheck 0.11.0 · branch `audit/2026-09-13`

## The two halves of this finding are not equally serious

The row puts two problems together. The fix must not pretend they are the same weight:

1. **The real exposure — every write target was a fixed name in the shared, world-writable
   `/tmp`.** All nine `>` redirects in the pre-fix tree (`:112, :139, :148, :194, :291, :295,
   :309, :328, :337`) open their file with plain truncation at a name any local user can
   create. `>` follows a symlink, so a local user who plants `/tmp/brew-install.log` (or any of
   the others) as a symlink makes the run truncate whatever that symlink points at, as long as
   the provisioning account can write it. The run is a confused deputy: it needs no root to do
   that damage, and the account usually holds a cached sudo credential. This is exploitable by
   anyone with write access to `/tmp` while provisioning runs — exactly the precondition the
   finding records. It is the security bug.

2. **Defence in depth — the image the script loaded was never re-verified.** `docker load`
   trusts the tarball, and the guard in front of it (`docker image inspect "${SEARXNG_IMAGE}"`)
   proves only that the pinned *reference* is absent, not that the tarball carries it. The
   container is always **run** by the digest-pinned reference `${SEARXNG_IMAGE}`, and that
   reference is the control which stops a substituted tarball from executing — so this is not the
   primary exposure. What was missing was a fail-closed check on the load the script itself
   performs: nothing compared what landed against the pin, and "the canary answers JSON" proves
   only that *something* serves JSON, not that it is the pinned image. The pre-fix code had no
   equivalent of that check; it is added here.

Both are fixed, and the evidence below is explicit about which is which.

## The fix

Every artefact of a run now lives in one unpredictable, `0700` directory created with `mktemp`,
and an `EXIT` trap removes it on the success path and on the `fail` path (which exits). The
directory is created through a function so it can be exercised without provisioning a node:

```bash
make_provision_tmp() {
    local dir
    dir="$(mktemp -d)" || return 1
    install -d -m 700 "${dir}" || return 1
    printf '%s\n' "${dir}"
}

PROVISION_TMP="$(make_provision_tmp)" \
    || fail "could not create a private temporary directory for the provisioning logs"

cleanup_provision_tmp() {
    local status="$1" log
    [ -n "${PROVISION_TMP:-}" ] || return 0
    if [ "${status}" -ne 0 ]; then
        for log in "${PROVISION_TMP}"/*.log; do
            [ -f "${log}" ] || continue
            echo "--- ${log} (last 40 lines) ---" >&2
            tail -n 40 "${log}" >&2
        done
    fi
    rm -rf "${PROVISION_TMP}" \
        || say "could not remove the private temporary directory ${PROVISION_TMP}"
}
trap 'cleanup_provision_tmp $?' EXIT
```

The cleanup dumps the tail of each log on a failed run before removing the directory, because
`fail` has just told the operator to look at a log that is about to disappear; the tail is
bounded so a chatty install cannot bury the real error. The removal itself is `|| say` rather
than `|| fail`: the trap runs while the script is already exiting, so `fail` there would recurse.

All nine log targets are now `"${PROVISION_TMP}/<name>.log"`, including the two `brew` failures
that were only reported with `say` and the two `docker` container logs.

The tarball is an explicit input, staged into the private directory by the loader, and the
loaded digest is compared to the pin before the canary:

```bash
SEARXNG_IMAGE_TAR="${SEARXNG_IMAGE_TAR:-}"

load_pinned_image() {
    local source="$1"
    local staged="${PROVISION_TMP}/searxng-image.tar"
    local loaded_digest
    cp "${source}" "${staged}" \
        || fail "could not stage ${source} in ${PROVISION_TMP}"
    docker load -i "${staged}" > "${PROVISION_TMP}/docker-load.log" 2>&1 \
        || fail "docker load failed; see ${PROVISION_TMP}/docker-load.log"
    loaded_digest="$(docker image inspect --format '{{index .RepoDigests 0}}' "${SEARXNG_IMAGE}" 2>/dev/null)"
    if [ "${loaded_digest}" != "${SEARXNG_IMAGE}" ]; then
        fail "the image loaded from ${source} is not the pinned ${SEARXNG_IMAGE} (RepoDigests: '${loaded_digest}'); refusing to run it"
    fi
}

if docker image inspect "${SEARXNG_IMAGE}" >/dev/null 2>&1; then
    say "searxng image already present"
elif [ -n "${SEARXNG_IMAGE_TAR}" ]; then
    [ -f "${SEARXNG_IMAGE_TAR}" ] \
        || fail "SEARXNG_IMAGE_TAR is set but is not a file: ${SEARXNG_IMAGE_TAR}"
    say "loading searxng image from ${SEARXNG_IMAGE_TAR}"
    load_pinned_image "${SEARXNG_IMAGE_TAR}"
else
    say "pulling searxng image from the internet"
    docker pull "${SEARXNG_IMAGE}" > "${PROVISION_TMP}/docker-pull.log" 2>&1 \
        || fail "docker pull failed; see ${PROVISION_TMP}/docker-pull.log"
fi
```

A behavioural change for operators: the tarball is **no longer** picked up implicitly from
`/tmp/searxng-image.tar`. It must be named explicitly —
`SEARXNG_IMAGE_TAR=/path/to/searxng-image.tar provision-node.sh` — which is what the
finding's expected-correct asks for. If the variable is unset the image is pulled by digest, as
before; if it is set but is not a file, the run stops instead of silently pulling.

## Not executed, on purpose

Provisioning itself was not run: it would install a container runtime on the fleet and restart a
live SearXNG instance, which the handover forbids. `docker load` was not run against the node's
live daemon either, so the harness stubs the `docker` CLI and no container was started or
changed.

One thing **was** checked against the live daemon, read-only, to confirm the comparison is in the
right format — a correctly provisioned image reports the pin as its first repo digest:

```
$ docker image inspect --format '{{index .RepoDigests 0}}' \
      'searxng/searxng@sha256:e084201aa606fafce2151c8dc2844c9c3309025e90fbe7163b4f5e5183e474f0'
searxng/searxng@sha256:e084201aa606fafce2151c8dc2844c9c3309025e90fbe7163b4f5e5183e474f0
```

The rest is **unverified** and is not claimed:

* Whether this Docker version records a tarball-supplied `RepoDigests` verbatim or derives it
  from content. If it records it verbatim, a deliberately crafted tarball could claim the pin
  while carrying different content and pass the comparison. The read-only probe above does not
  settle that: it shows what a normally provisioned image reports, not what `docker load` writes
  for a tarball. The check is still worth having — it fails closed on the mismatch it *can* see,
  and on a load that produced no repo digest at all — but it is defence in depth and is not
  presented as a substitute for the digest-pinned `docker run` reference, which remains the
  control.
* `mktemp -d` was measured to produce mode `0700` with two calls never colliding, and on this
  platform it lands under the per-user `$TMPDIR`; if `$TMPDIR` were ever a shared directory the
  unpredictability and the `0700` mode are what protect it, not the parent.

The log-tail dump on the failure path is an addition beyond the finding's expected-correct. It
exists to keep the `|| fail "… see <path>"` messages honest once the directory is removed; it is
bounded to 40 lines per log.
