# B102 — a cross-scheme redirect surfaced as an opaque transport error

Host: node1 (arm64, macOS 26.6.2, Swift 6.3.3) · branch audit/2026-09-13

## What was wrong

`DirectHTTPFetcher` follows redirects manually so every hop can be re-validated by
`URLPolicy`. A redirect that changes scheme does not reach that loop: `URLSession` does not
consult `NoRedirectDelegate.willPerformHTTPRedirection` for a cross-scheme hop, refuses it
internally, and reports a file-system `URLError`. The fetcher's catch-all mapping then produced:

```
$ swift test --scratch-path "$SCRATCH" --filter "FetchRedirectTests/testARedirectToAFileURLIsRefusedWithoutReadingTheFile"
.../FetchRedirectTests.swift:152: error: ... XCTAssertEqual failed: ("the transport reported error -1102") is not equal to ("the server redirected to a local file, which is not fetched") - the refusal must be legible, not an opaque transport code
.../FetchRedirectTests.swift:158: error: ... XCTAssertFalse failed - the raw URLError code must not reach the caller: the transport reported error -1102
```

The observable security outcome was already correct — no local content came back, even for a
readable `/etc/hosts` — but the caller got an opaque code and could not tell a cross-scheme
refusal from any other transport failure.

## The fix, and one honest limitation

`DirectHTTPFetcher` now maps the file-system transport codes (`-1100 fileDoesNotExist`,
`-1101 fileIsDirectory`, `-1102 noPermissionsToReadFile`) to a reason that states the policy
position:

```swift
case .fileDoesNotExist, .fileIsDirectory, .noPermissionsToReadFile:
    // A redirect to `file://` never reaches the manual loop: `URLSession` does not
    // consult `willPerformHTTPRedirection` for a cross-scheme hop, so it refuses it
    // internally and reports one of the file-system codes. ...
    throw SearchError.fetchFailed(
        request.url,
        reason: "the server redirected to a local file, which is not fetched"
    )
```

`URLPolicy`'s doc comment now records that this one hop is decided beneath it, so the limit is
documented where the policy is described rather than left implicit.

**The refusal cannot literally come from `URLPolicy`.** The task brief asked for the refusal to
come from policy, and this is the one part of that I could not do: `URLSession` never surfaces the
redirect target for a cross-scheme hop, so `policy.validate` is never called with it and no
`Decision` exists to return. The only in-process alternatives were to probe the target ourselves
before asking the transport to fetch it — duplicating the request and its policy hop — or to stop
using `URLSession` for redirects altogether. Both are larger than this finding. What the fix does
deliver is a legible, policy-shaped reason and a documented limitation instead of an undocumented
reliance on transport behaviour.

It is deliberately still a `fetchFailed`, not a `blockedURL`: the blocked URL is the `file:` target
we never see, so `blockedURL(currentURL)` would name the entry URL and claim a decision that was
not made about it. `blockedURL` also suppresses the Jina fallback; the ledger's candidate fix asks
for the diagnosis change and to keep the regression test that pins the observable outcome, so the
error category is unchanged.

## The test

`FetchRedirectTests.testARedirectToAFileURLIsRefusedWithoutReadingTheFile` — the existing
regression test the finding asked to keep — now asserts the exact legible reason, still asserts
that no local content (`localhost` from `/etc/hosts`) appears anywhere in the error, and adds that
the opaque `transport reported error` text is gone. It remains the pin that the file is never read
and that exactly one request is made.

## Noted, not changed

The other redirect-scheme cases (`ftp:`, `data:`) are not covered by this branch; only the
file-system codes the probe produces are mapped. A redirect to another unsupported scheme still
reaches the generic `the transport rejected the request URL` reason, which is inaccurate but not
opaque and not part of this finding.
