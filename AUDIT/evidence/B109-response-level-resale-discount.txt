# B109 — the response-level resale discount overrode the per-result attribution

Host: this Mac (arm64, macOS 26.6.2, Swift 6.3.3) · branch audit/2026-09-13

## What was wrong

`RankFusion.fuse` documented — in the comment directly above the code — that the aggregator
discount is decided **per result**, because one aggregator instance can serve one page from
Brave and another from an engine nobody else owns. It then ORed the response-level answer into
the per-result answer anyway:

```swift
// RankFusion.swift, before
let responseResellsOwnedIndex = RankFusion.resellsIndexAlreadyOwned(
    response: response, ownedFamilies: ownedFamilies)
...
rawWeight: weight(
    for: contributionFamily, provider: provider, base: base,
    duplicatedOwnedIndex: responseResellsOwnedIndex || resoldFamily != nil,
    configuration: configuration)
```

Two consequences, both reachable whenever a local SearXNG (or Open Web Search) response reports
engines for the whole response and for individual results:

| # | Where | Defect | Effect |
|---|-------|--------|--------|
| 1 | `fuse`, `duplicatedOwnedIndex:` | The response-level flag was ORed into every result, so one resold page discounted **all** of its siblings — including pages whose own `upstreamEngines` name nobody else's index. | The per-result refinement the comment promises did nothing once the response-level list also matched. |
| 2 | `resellsIndexAlreadyOwned` | It omitted the `family.isIndependentIndex` guard that the per-result `resoldFamily` applies, so a response-level hit on Google or DuckDuckGo counted as duplicating an "owned index". | The same provenance was judged differently depending on which level the adapter reported it at, and a non-owned family was treated as an owned one. |

`response.upstreamEngines` is populated by the aggregator adapters (`SearXNGProvider.swift:107-111,153`,
`OpenWebSearchProvider.swift:116-120,157`), and both adapters also populate per-result
`upstreamEngines` when the vendor reports `engine`/`engines` per item
(`SearXNGProvider.engines(of:)` returns `nil` when the item carries none). So a response could
legitimately carry both, which is exactly the case that was mishandled.

## The fix

The response-level answer is now only the fallback for a result that carries no attribution of
its own; a result with its own `upstreamEngines` is judged on that alone.

`resellsIndexAlreadyOwned` now applies the same `isIndependentIndex` guard as `resoldFamily`,
and its doc comment states that the two must agree. No public signature changed; `weight` is
untouched.

## The tests

Three tests were added to `Tests/WebSearchCoreTests/FusionAndReliabilityTests.swift` (in
`RankFusionTests`), and `testUpstreamEngineMappingDetectsDuplication` was extended:

* `testAggregatorDiscountIsPerResultEvenWhenTheResponseNamesAnOwnedIndex` — the response-level
  list names Brave while the two results name Brave and Wikipedia respectively. Asserts the
  resold page scores `1/61 + 0.7/61` and its sibling keeps the full `1/62`. Under the old OR this
  was the only test that distinguished the two levels and it failed.
* `testAggregatorDiscountFallsBackToResponseLevelWithoutPerResultEngines` — pins the fallback, so
  a later change cannot drop it: with both results carrying no attribution, a response-level
  Brave hit must discount both (`0.7/62`).
* `testResponseLevelDiscountIgnoresNonIndependentFamilies` — a directly configured Startpage
  (family `.google`) plus a SearXNG response whose response-level list is `google`; the
  aggregator must keep the full `1/61`.
* `testUpstreamEngineMappingDetectsDuplication` gains a direct assertion that
  `resellsIndexAlreadyOwned` returns false for `ownedFamilies: [.google]` with a `google`
  upstream engine.

## Noted, not changed

The response-level fallback deliberately does not fold the contribution family the way the
per-result path does — with only a response-level list there is no way to say *which* result
belongs to the owned index, so the whole response is discounted but keeps the aggregator's own
family. That asymmetry is pre-existing and is covered by
`testAggregatorAloneIsDiscountedAgainstIndependentIndex`; this task only stopped the
response-level answer from overriding a per-result one.
