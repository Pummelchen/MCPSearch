# B16 — a PDF was claimed as readable text

Host: MacBook-AB.local (arm64, macOS 26.6.2) · branch audit/2026-09-13

## What was wrong

`application/pdf` was on the production content-type allow-list, and the only non-HTML branch of
`DirectHTTPFetcher` decodes a body as UTF-8 or Latin-1. A PDF therefore reached the model as
tens of thousands of characters of `%PDF-1.7 … stream …` gibberish, labelled `raw_text`, with a
`truncated` flag that made it look like a clipped *document*. There is no PDF handling anywhere in
the package (`grep -rn pdf Sources` matched only the allow-list entry).

## Fails-before evidence

```
$ swift test --filter FetchFallbackTests/testAPDFIsRefusedByTheDirectFetchButStillReadableByTheReader
  # with application/pdf back on the allow-list:
  failed - a PDF must not be returned as text: raw_text, 67 characters
```

## The fix

`application/pdf` is off the list, so the direct fetch refuses it with `extractionFailed` — the
honest answer, since nothing here can read a PDF. The reader fallback still serves it: Jina
renders PDFs remotely, and `WebFetcher` consults the reader exactly when the direct fetch fails,
so a configured reader turns a PDF into markdown as before.

The test asserts both halves: the direct fetch throws `extractionFailed` rather than returning echo `raw_text`, and the same URL through `WebFetcher` with a reader configured comes back with
`method == .jinaReader` and the reader's text.
